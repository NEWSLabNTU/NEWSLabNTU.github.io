Detailed Description

Issue 2009 — the requests ONE poll client has in flight, as an intrusive list of the futures waiting on them, each keyed by its request's sequence id. A reply is delivered only to the future whose id it carries; a reply naming no pending future (a removed or destroyed one's) is dropped.

The same rule as Rust's nros_rmw::RequestCorrelator, which every other client surface uses. It lives in the futures here rather than in a table because each future already owns the buffer its reply must land in.

BOUNDED, NO HEAP, NO CAPACITY TO MIS-SIZE: an entry is a future the caller already holds, so the list is as long as the futures in flight. What caps that is the transport's own outstanding-request limit (zenoh NROS_ZENOH_MAX_PENDING_GETS, Cyclone's 8 per client): a send past it is refused by the backend, and send_request then returns an empty future (valid() false) without linking anything.

A backend that cannot assign ids (SEQUENCE_ID_UNKNOWN) gets one request in flight per client — can_send() refuses a second while the first is pending — and an unkeyed reply goes to the sole pending future. A removed unkeyed request costs the next unkeyed reply (orphans), which is dropped rather than delivered to a newer request it cannot be told apart from.

Issue 2027 — what the OWNER of this list does when a goal-keyed future is abandoned (cancelled, destroyed, moved over) before its reply: the action client frees the request's slot in the Rust core unless something else still waits on that reply.
