Detailed Description

template<typename T, size_t Cap = ::rclcpp::rx_buffer_capacity<T>::value>
class rclcpp::Future< T, Cap >

Single-shot deferred result for request/response operations.

Returned by PollClient<S>::send_request (phase-456 W9; it was Client<S>::send_request before the split). The future is consumed when the result is taken – move-only, single-shot.

Usage:

auto fut = client.send_request(req);
ResponseType resp;
RCLCPP_TRY(fut.wait(executor.handle(), 5000, resp));

Template Parameters
CapBytes the RECEIVE buffer holds. Defaults to T's own derived bound where it has one, and to the legacy T::SERIALIZED_SIZE_MAX estimate where it does not. The _sized escape hatches are Client::send_request_sized and ActionClient::get_result_future_sized, which hand back a Future<T, N> (issue 0964). This buffer IS the capacity: under-sizing it truncates the reply.

A service future is KEYED BY ITS REQUEST'S SEQUENCE ID (issue 2009): any number of futures may be in flight on one PollClient, each receives only the reply to its own request whichever future happens to poll first, and a reply that arrives after the future was cancelled, removed (remove_pending_request) or destroyed is dropped — never handed to a later future. See detail::PendingList for the bound and for backends that cannot assign ids.

An ACTION future (rclcpp_action::Client<A>::send_goal_future / get_result_future) is KEYED BY ITS GOAL the same way (issue 2011): it is on its client's list of acceptances or of results, it receives only its own goal's, and a reply for a goal nobody waits on — or arriving after the future was cancelled or destroyed — is dropped. Two action clients keep two sets of lists, so they never see each other's replies.

Check if the result has arrived (non-blocking).

For a service future this takes replies off the client until its own arrives: one for another pending future is handed to that future, one for no pending future is dropped (at most detail::MAX_STALE_DRAIN_PER_POLL per call).
