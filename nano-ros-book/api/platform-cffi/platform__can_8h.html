Detailed Description

Canonical C ABI for the nros platform CAN frame driver.

Companion to <nros/platform.h>. An application that sends its own CAN or CAN FD frames (an actuator command, a heartbeat) sends them through these five calls. Carved into a separate header because a board with no CAN never includes it.

What the driver does and does not do

The driver opens a device that the board already brought up and moves frames on it. It sets no bitrate, starts no controller and states no layer-1 fact. Frame ids, payload layout, classic or FD, and any end-to-end protection belong to the application.

The backend

Exactly one backend defines these symbols in an image, and it follows from the board: Zephyr's CAN API on a Zephyr board, SocketCAN on a Linux-process board, the board package's own driver on a "board"-stack board, or the host-only mock where the image selects it.

Handle storage

nros_platform_can_t is caller storage of a size this header fixes. A backend keeps its state inside it and proves at compile time that the state fits (NROS_PLATFORM_CAN_STORAGE_FITS). Zero-initialise a handle before its first open; close returns it to the closed state. An open handle must not move: a backend may keep a kernel object (a semaphore, a message queue) inside it.

Return values

0 (NROS_PLATFORM_CAN_OK) on success, a negative NROS_PLATFORM_CAN_E* code otherwise. timeout_us = 0 never blocks. send returning 0 means the controller accepted the frame within timeout_us; with NROS_PLATFORM_CAN_SEND_WAIT_TX set in the frame's flags it means the frame left the controller. A backend that cannot report completion returns NROS_PLATFORM_CAN_ENOTSUP for that flag and never downgrades it to acceptance.

◆ nros_platform_can_open()

int8_t nros_platform_can_open ( nros_platform_can_t * can,
const char * device,
uint8_t want_fd )

Open device into the caller's handle storage. device NULL opens the image's device (the one its board stack names); a non-NULL name opens that device instead. want_fd non-zero asks for CAN FD: afterwards nros_platform_can_fd_active says whether FD is active. A backend that can tell at open that the device does not carry FD (SocketCAN: the interface MTU) fails here with NROS_PLATFORM_CAN_ENOFD; one that learns it from the device's mode (Zephyr: the controller's CAN_MODE_FD, set at bring-up) opens and reports it through fd_active. Either way an FD send on a handle whose FD is not active returns NROS_PLATFORM_CAN_ENOFD.
