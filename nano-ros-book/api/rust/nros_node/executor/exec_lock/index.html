phase-509 P9b – the executor’s lock (RFC-0108 “As built in P9b”). phase-509 P9b item 1 (RFC-0108 “As built in P9b”) – the executor’s lock.

RFC-0108 runs one executor per core with one worker thread per preemption level. Every path that touches the executor’s state – a worker’s pass, and every C / C++ FFI entry a callback or another thread calls – then has to be serialised, and that is this lock: a port-provided, RECURSIVE, PRIORITY-INHERITING mutex (nros_platform_mutex_rec_* on every port), which the runner installs on the executor before a second thread can reach it.

An executor with no lock installed (every one-level image, every Rust &mut user) takes the None arm: a guard is one predictable branch and nothing else, so this seam changes no behaviour where it is not installed.

Why recursive: until the pass releases the lock around each user callback (item 2), a callback that calls back into the executor (timer_cancel, *_release, a parameter call) re-enters the lock the spinning worker already holds, on the same thread.

Why priority-inheriting: a less urgent worker holding the lock for a bookkeeping step must run at the waiter’s priority, so a more urgent level’s blocking is bounded by ONE critical section (RFC-0108 B_i).

Interrupt handlers never take it: arrivals go through the scheduler’s lock-free ready word and the wake object, exactly as before.

ExecLock
The executor’s lock: the port’s recursive priority-inheriting mutex and the two calls that take and give it. Installed once, before any second thread can reach the executor (super::Executor::set_exec_lock), and never changed while one can.
