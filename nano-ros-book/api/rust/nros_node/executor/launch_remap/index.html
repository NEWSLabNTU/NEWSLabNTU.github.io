Launch remap rules as ONE const table in flash – issue 1971, RFC-0107 step 1.

The launch file’s <remap from= to=/> rules describe the IMAGE, not one executor. Before this every executor carved a RAM table of 16 rules (RemapRule, 404 B each on thumbv7em: 6,464 B per backing) and the generated C/C++ entry filled it with one nros_cpp_declare_remap call per rule, on every tier’s executor. Now codegen emits the rules once, as a static const array of string pointers, and hands it to the runtime once (set_launch_remaps, nros_cpp_set_launch_remaps) before any tier is set up. Every executor reads that table; none copies it.

Layering is unchanged: these rules are the AUTHORITATIVE tier of crate::names::resolve_name_layered, and --ros-args -r rules (still in the executor’s RAM table, see ExecutorSizing::remaps) are the fallback.

The Rust entry already worked this way: its launch remaps are a &'static slice on RuntimeCtx, and this table is the C/C++ twin of it.
