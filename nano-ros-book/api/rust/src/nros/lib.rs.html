1//! # nros
2//!
3//! A lightweight ROS 2 client library for embedded systems.
4//!
5//! This crate provides a unified API for building ROS 2 nodes in Rust,
6//! with support for `no_std` environments and embedded targets.
7//!
8//! ## Features
9//!
10//! - **no_std compatible**: Works on bare-metal and RTOS targets
11//! - **Zero-copy where possible**: Minimizes memory allocations
12//! - **Type-safe**: Compile-time verification of message types
13//! - **ROS 2 compatible**: Interoperates with standard ROS 2 nodes via rmw_zenoh
14//!
15//! ## Quick Start
16//!
17//! ```ignore
18//! use nros::prelude::*;
19//! use std_msgs::msg::Int32;
20//!
21//! let config = ExecutorConfig::from_env().node_name("my_node");
22//! let mut executor = Executor::open(&config)?;
23//!
24//! let node = executor.node_builder("my_node").build()?;
25//! let publisher = executor.node_mut(node).create_publisher::<Int32>("/my_topic")?;
26//! publisher.publish(&Int32 { data: 42 })?;
27//!
28//! executor.node_mut(node).create_subscription::<Int32, _>("/topic", |msg: &Int32| {
29//!     println!("Received: {}", msg.data);
30//! })?;
31//!
32//! executor.spin_blocking(SpinOptions::default());
33//! ```
34//!
35//! ## Executor Sizing
36//!
37//! The executor's static memory layout is controlled via environment variables
38//! at build time:
39//!
40//! - **`NROS_EXECUTOR_MAX_CBS`** (default 4) — maximum number of registered
41//!   callbacks (subscriptions + timers + services + guard conditions).
42//! - **`NROS_EXECUTOR_ARENA_SIZE`** (default 4096) — byte budget for storing
43//!   callback closures inline.
44//!
45//! A subscription's arena receive buffer is sized from the MESSAGE TYPE's own
46//! serialized bound (phase-392 W3c), not from that knob, wherever the bound is
47//! reachable. `.rx_buffer::<N>()` is the opt-out: it says "give me exactly `N`
48//! bytes per slot" and skips the derivation, which is what a peer that pads or
49//! a `.msg` bound looser than the traffic needs (e.g.
50//! `node_mut(id).subscription(t).typed::<M>().rx_buffer::<4096>().build(cb)`).
51//!
52//! ## Transport Backends
53//!
54//! Phase 248 C5c — `nros` is RMW- and platform-AGNOSTIC. It carries only the
55//! `rmw-cffi` vtable; the concrete backend (zenoh / xrce / cyclonedds) enters
56//! the link graph via the board crate (embedded), the board-less app's own
57//! `nros-rmw-*` dep (native), or the `nros-c`/`nros-cpp` staticlib root (D3),
58//! and self-registers through the `RMW_INIT_ENTRIES` walker at `Executor::open`.
59//! The concrete session type is resolved automatically; advanced users can
60//! access it via `nros::internals::RmwSession`.
61//!
62//! ## Crate Features
63//!
64//! `nros` exposes only FUNCTIONAL features — `std`/`alloc`, the `rmw-cffi`
65//! vtable, `lending`, `bridge`/`config`, `param-services`,
66//! `lifecycle-services`, `safety-e2e`, `stream`, `ffi-sync`, and the ROS
67//! edition (`ros-humble`/`ros-iron`). There are NO `platform-*` or concrete
68//! `rmw-*` selector features (Phase 248 C7). Platform + RMW are selected by the
69//! board / staticlib root via dependencies, not `nros` features. The
70//! `zephyr_component_main!` entry macro is gated only on `rmw-cffi` (it's
71//! framework entry codegen, like `nros::main!`), not a platform feature.
72//!
73//! **ROS edition** (select one; RFC-0056 — the per-distro interop profile):
74//! - `ros-humble` - ROS 2 Humble (default; `TypeHashNotSupported`, XCDR1)
75//! - `ros-iron` - ROS 2 Iron (RIHS01 type hash)
76//! - `ros-jazzy` - ROS 2 Jazzy (RIHS01; XCDR2/appendable is phase-303)
77//!
78//! **Other**:
79//! - `std` (default) - Enable standard library support
80//! - `alloc` - Enable heap allocation without full std
81//!
82//! ## Further Reading
83//!
84//! - [`guide`] — tutorials: getting started, services, configuration,

228// Logging (phase-417 W4.d, issue 0589).
229//
230// `nros_log` was in this crate's dependency graph and reachable from NONE of
231// its surface: no `pub use`, nothing in the prelude. So from the façade the
232// shortest path to "print something" was `std::println!` — which is FATAL on
233// Zephyr `native_sim`: `zvfs_write(1, …)` dispatches to
234// `stdinout_write_vmeth`, which calls `zvfs_write(1, …)` again, and because
235// `k_mutex` is recursive it exhausts the stack instead of deadlocking. The
236// image dies with no message. A logging facade nobody can reach from the
237// umbrella is not a facade.
238//
239// `nros::Logger` IS RE-BOUND, and that is the point rather than a side effect.
240// It used to name `nros_core::logger::Logger`, which formats through the `log`
241// crate: on a target with no `log` backend installed — every embedded one —
242// the record is constructed and dropped, and it NEVER reaches
243// `nros_platform_log_write`. The type the C and C++ FFI hands out, the type
244// the `nros_*!` macros dispatch through, and the type the platform sink
245// receives is `nros_log::Logger`. One name, one meaning.
246//
247// Migration: the two types share `new` and `name` and NOTHING else — the old
248// one has inherent `.info(&str)` / `.warn(&str)` / `*_once` / `*_throttle`
249// methods, the new one is driven by the `nros_*!` macros. So every call site
250// that used the old surface FAILS TO COMPILE against the new binding rather
251// than silently changing where its records go. That is the RFC-0089 rule
252// applied to our own rename, and it is why this is a re-binding with a named
253// escape hatch instead of a quiet swap. The escape hatch is
254// [`LogCrateLogger`], deprecated on arrival.
255pub use nros_log::{
256    DEFAULT_LOGGER, LogSink, Logger, MAX_LOGGERS, Record as LogRecord, Severity, ThrottleState,
257    get_logger, get_or_create_logger, register_logger,
258};
259// The emission macros, at the crate root, because a user who has
260// `use nros::prelude::*` should not have to learn a second crate name to log a
261// line. `#[macro_export]` puts them at `nros_log`'s root; this puts them at
262// ours.
263//
264// NAMES (phase-417, RFC-0089 "each language follows ITS OWN upstream",
265// settled 2026-09-04). The three ROS 2 client libraries disagree about how to
266// spell a log line — `rclrs::log_info!`, `RCLCPP_INFO`,
267// `RCUTILS_LOG_INFO_NAMED` — so there is no one "ROS 2 spelling" to match.
268// Rust follows rclrs, because a node ported from rclrs is read beside rclrs.
269// Hence the five severity macros below carry rclrs's names.
270//
271// Two families keep OUR prefix, and that is a decision rather than an
272// oversight: a name takes rclrs's spelling exactly when rclrs HAS that name.
273//
274//   * `nros_trace!` — rclrs stops at `debug`. TRACE has no upstream twin, so
275//     giving it one would claim a correspondence that does not exist.
276//   * `nros_*_throttle!` / `nros_*_throttle_at!` — rclrs throttles with a
277//     MODIFIER on one macro (`log_info!(logger.throttle(d), "…")` via
278//     `LogParams` / `ToLogParams`), not a macro per severity. Adopting that is
279//     a shape change, not a rename; see `nros-log/src/macros.rs`'s throttle
280//     note for the three ledger rows it would have to reverse.
281pub use nros_log::{
282    log_debug, log_error, log_fatal, log_info, log_warn, nros_debug_throttle,
283    nros_debug_throttle_at, nros_error_throttle, nros_error_throttle_at, nros_fatal_throttle,
284    nros_fatal_throttle_at, nros_info_throttle, nros_info_throttle_at, nros_trace,
285    nros_trace_throttle, nros_trace_throttle_at, nros_warn_throttle, nros_warn_throttle_at,

566/// Route this image's panics to its platform — phase-366 W5.c / RFC-0077.
567///
568/// Emits the `#[panic_handler]` for an embedded image, forwarding the message
569/// to `nros_platform_panic` so a Rust panic ends the same way a C precondition
570/// failure or a C++ terminate does. What that ending IS belongs to the port:
571/// `k_panic()` on Zephyr, `esp_system_abort()` on ESP-IDF, UART-then-exit-QEMU
572/// on the ThreadX RV64 board.
573///
574/// # Why this is a macro you INVOKE, not something `nros::main!` emits
575///
576/// `#[panic_handler]` is a singleton of the final artifact, and the image owns
577/// it. Emitting one silently from `nros::main!()` would collide with every image
578/// that already declares its own — `examples/qemu-esp32-baremetal` writes
579/// `use esp_backtrace as _;`, and `logging-smoke-freertos-mps2` uses
580/// `panic-semihosting` with `features = ["exit"]` so a panic exits QEMU instead
581/// of hanging the test harness. Those images are RIGHT, and an invisible default
582/// would fight them.
583///
584/// So the line is written in the entry, where it can be read, swapped for
585/// `use panic_halt as _;`, or replaced by a hand-written handler that logs to
586/// NVM and reboots. A default you cannot see is a constraint, not a default.
587///
588/// # Use — `main!(panic = …)` is the normal way; this is the escape hatch
589///
590/// phase-366 R3. An entry that goes through `nros::main!()` should say
591/// `panic = "platform"` (or nothing — that is the default since M5) and let the
592/// macro emit this body. One line, and the build can check it.
593///
594/// ```ignore
595/// #![no_std]
596/// nros::main!();            // ends through `nros_platform_panic`
597/// ```
598///
599/// Invoke this macro directly only where no `main!()` expansion can carry the
600/// item — a hand-rolled `no_std` binary, or the lib side of a crate whose
601/// `crate-type` includes `staticlib` and whose entry macro is
602/// `zephyr_component_main!` / a board `app_main!`. It is kept for exactly those:
603/// deleting it would strand the images that cannot use the macro replacing it.
604///
605/// ```ignore
606/// // src/app_main.rs — the .a is a final artifact to rustc, and `main!()` in
607/// // the bin target never reaches it.
608/// nros::panic_to_platform!();
609/// ```
610///
611/// Do NOT invoke it in a `std` image: libstd supplies the lang item there and a
612/// second one does not compile. Do not invoke it alongside `use panic_halt as _`
613/// or any other provider, for the same reason — that is the duplicate
614/// `check-archive-lang-items` exists to catch.
615/// Park the core on panic — the `halt` value of `nros::main!(panic = …)`.
616///
617/// For an image that must not print: no formatting, no allocation, no call out
618/// to the platform. Interrupts are masked first so the parked core cannot be
619/// woken back into a half-dead system by a timer or a driver ISR still armed
620/// from before the panic.
621///
622/// This is a body rather than a re-export of the `panic-halt` crate so that
623/// choosing it costs the entry no new dependency — `main!(panic = "halt")` is a
624/// word in a macro the crate already calls, which is the point of the surface.
625/// The behaviour is the same: mask, then spin forever.
626///
627/// Prefer `panic = "platform"`. Halting discards the diagnosis, and every port
628/// implements `nros_platform_panic` precisely so a dying image can say why.
629/// Phase 392 W3b — the receive-buffer size for a message type, as a constant
630/// that cannot drift from the type.
631///
632/// ```ignore
633/// node.subscription::<PointCloud2>("points")
634///     .rx_buffer::<{ nros::rx_buffer_for!(PointCloud2) }>()
635///     .build(on_cloud)?;
636/// ```
637///
638/// `.rx_buffer::<N>()` has always accepted a number. The problem is where the
639/// number comes from: a literal is correct until someone appends a field to the
640/// message, and then it is silently too small — the sample is received, ACKed
641/// and dropped at the transport, which needs a packet capture to attribute
642/// (`report_dropped_take`, and the 13.4 KiB Autoware trajectory case). This
643/// expands to the type's own bound, computed from its schema by phase 380, so
644/// appending a field moves the buffer with it.
645///
646/// **phase-392 W3c narrowed what this is FOR.** A plain
647/// `.typed::<M>().build()` now derives its arena receive buffer from `M` on its
648/// own, and `.rx_buffer::<N>()` is the opt-out, so the macro is no longer how a
649/// buffered subscription gets a type-sized buffer. What still needs it is the
650/// entry shapes whose buffer is a real inline `[u8; RX]` and therefore a
651/// const-generic argument: `.message_info()` and `.safety()`. Those are the
652/// call sites this expands for.
653///
654/// **Why a macro and not a method.** The builder cannot do this for you:
655/// inside `impl<M> TypedSubscriptionBuilder<M>` the type is a generic
656/// parameter, and on stable Rust a generic parameter may not appear in a const
657/// operation — `error: generic parameters may not be used in const operations`.
658/// At a call site the type is CONCRETE, which is legal, so the size has to be
659/// named where the type is. That constraint is also why phase-392's size
660/// classes were "decoupled from codegen" in the first place.
661///
662/// **Unbounded types are a BUILD ERROR** (phase-403 W0). A type with an
663/// unbounded `string`/`wstring`/`sequence` has no bound, and this refuses to
664/// invent one. It used to expand to `DEFAULT_RX_BUF_SIZE`; it now fails to
665/// compile, naming both remedies.
666///
667/// Every message type is REQUIRED to carry a derived upper bound, stated in the
668/// `.msg` (`string<=64`) or capped in `nros-codegen.toml`. Phase 380 is explicit
669/// that `None` means "no bound EXISTS", never "unknown", and that a buffer must
670/// not be sized from a fallback. Substituting the configured default was the
671/// violation of that rule; refusing is what it licenses. `report_dropped_take`
672/// is a backstop for a buffer that is too small, not a licence to pick one.
673///
674/// ```compile_fail
675/// use nros_serdes::schema::{Field, FieldType, Message};
676/// struct Unbounded;
677/// impl Message for Unbounded {
678///     const TYPE_NAME: &'static str = "test/msg/Unbounded";
679///     const FIELDS: &'static [Field] = &[Field {
680///         name: "s",
681///         ty: FieldType::String,
682///         offset: 0,
683///     }];
684/// }
685/// let _n: usize = nros::rx_buffer_for!(Unbounded);
686/// ```
687///
688/// The positive control for that `compile_fail`, so it cannot pass because the
689/// fixture stopped compiling for an unrelated reason:
690///
691/// ```
692/// use nros_serdes::schema::{Field, FieldType, Message};
693/// struct Bounded;
694/// impl Message for Bounded {
695///     const TYPE_NAME: &'static str = "test/msg/Bounded";
696///     const FIELDS: &'static [Field] = &[Field {
697///         name: "a",
698///         ty: FieldType::Uint64,
699///         offset: 0,
700///     }];
701/// }
702/// let n: usize = nros::rx_buffer_for!(Bounded);
703/// assert!(n > 0);
704/// ```
705///
706/// **Why the `const` block.** The macro is used in two positions: as a
707/// const-generic argument (`.rx_buffer::<{ rx_buffer_for!(M) }>()`) and as a
708/// plain expression (`let n = rx_buffer_for!(M);`). A bare `panic!` is a build
709/// error in the first and a RUNTIME panic in the second, which would make the
710/// rule depend on where the macro appears. Wrapping the whole match in an inline
711/// `const` block forces compile-time evaluation in BOTH, so an unbounded type
712/// can never reach a running image.
713///
714/// **What the error names.** rustc points at this macro invocation, where the
715/// type is written literally, so the TYPE is named. The MEMBER that costs the
716/// bound cannot be in the message: const evaluation does not format, so a
717/// `panic!` there takes a literal only. The member is named by the codegen
718/// diagnostic for the same type -- `unbounded_reason` in the generated C header
719/// (`packs/c/message.h.jinja`), which names EVERY member that costs the bound in
720/// one build (phase-403 W0), or `nros_serdes::size::visit_unbounded` over its
721/// `FIELDS`.
722#[macro_export]
723macro_rules! rx_buffer_for {
724    ($msg:ty) => {
725        // The `const` block is load-bearing; see "Why the `const` block" above.
726        const {
727            match $crate::__rx_bound::<$msg>() {
728                ::core::option::Option::Some(n) => n,
729                ::core::option::Option::None => ::core::panic!(
730                    "nros: this message type has NO serialized-size bound, so no \
731                     receive buffer can be sized from it.\n\
732                     Every message type must carry a derived upper bound. Bound the \
733                     member that costs it, either:\n\
734                     \x20 - in the `.msg`: `string<=64`, `wstring<=64`, \
735                     `sequence<T, N>`, `T[<=N]`; or\n\
736                     \x20 - as an INLINE `cap` in `nros-codegen.toml`: under \
737                     `[fields]`, `\"pkg/Msg.field\" = 64`. A `heap` or `view` cap \
738                     is a sizing hint that nothing enforces (RFC-0033), so it \
739                     deliberately does NOT bound.\n\
740                     WHICH members cost the bound -- all of them, not just the \
741                     first -- are named by the codegen diagnostic for this same \
742                     type: `unbounded_reason` in the generated C header, or \
743                     `nros_serdes::size::visit_unbounded` over its `FIELDS`. The type itself is named by the \
744                     `rx_buffer_for!` invocation rustc points at.\n\
745                     Phase 380: `None` means no bound EXISTS, never \"unknown\", and \
746                     a buffer sized from a fallback is the failure that rule was \
747                     written to prevent. Erroring honours it; defaulting to \
748                     `DEFAULT_RX_BUF_SIZE` did not."
749                ),
750            }
751        }
752    };
753}

756macro_rules! panic_halt {
757    () => {
758        #[panic_handler]
759        fn __nros_panic_halt(_info: &::core::panic::PanicInfo) -> ! {
760            // Mask interrupts through the platform's critical section, which is
761            // the one IRQ primitive that is portable across the ports (the
762            // `cortex_m`/`riscv` intrinsics are not). Entering and never
763            // leaving is deliberate.
764            unsafe extern "C" {
765                fn nros_platform_critical_section_acquire() -> u32;
766            }
767            // SAFETY: the ABI's acquire takes no argument and returns a restore
768            // token we deliberately drop — nothing after this point runs.
769            unsafe {
770                let _ = nros_platform_critical_section_acquire();
771            }
772            loop {
773                ::core::hint::spin_loop();
774            }
775        }
776    };

779#[macro_export]
780macro_rules! panic_to_platform {
781    () => {
782        #[panic_handler]
783        fn __nros_panic(info: &::core::panic::PanicInfo) -> ! {
784            use ::core::fmt::Write as _;
785
786            // Fixed buffer, never the heap: this runs when the allocator may be
787            // exactly what failed. Truncation is deliberate — a short panic line
788            // still diagnoses; a missing one does not.
789            struct Buf {
790                bytes: [u8; 192],
791                used: usize,
792            }
793            impl ::core::fmt::Write for Buf {
794                fn write_str(&mut self, s: &str) -> ::core::fmt::Result {
795                    let room = self.bytes.len() - self.used;
796                    let n = s.len().min(room);
797                    self.bytes[self.used..self.used + n].copy_from_slice(&s.as_bytes()[..n]);
798                    self.used += n;
799                    Ok(())
800                }
801            }
802
803            let mut buf = Buf {
804                bytes: [0u8; 192],
805                used: 0,
806            };
807            let _ = write!(buf, "{info}");
808
809            unsafe extern "C" {
810                fn nros_platform_panic(msg: *const u8, len: usize) -> !;
811            }
812            // SAFETY: `buf.bytes[..used]` is initialised and outlives the
813            // diverging call; the ABI takes a length-delimited diagnostic, not
814            // a C string.
815            unsafe { nros_platform_panic(buf.bytes.as_ptr(), buf.used) }
816        }
817    };

820/// Define Zephyr's `rust_main` for a self-bringup Rust component package.
821///
822/// The macro is intended for `rust_cargo_application()` apps whose crate
823/// already invokes `nros::node!()`. It opens a Zephyr executor, registers
824/// the supplied component through [`ExecutorNodeRuntime`], and spins forever.
825/// Issue 0330 — force-link an RMW backend crate into a pure-Rust staticlib.
826///
827/// On a Rust-only image (Zephyr and friends) the Zephyr module emits a weak
828/// `nros_rmw_<name>_register` and calls it only if it resolves. The strong
829/// definition is the backend crate's `#[no_mangle]` export — and rustc's
830/// staticlib DCE drops it unless something in the crate being compiled into the
831/// staticlib references that crate. The symbol is then present in the rlib and
832/// absent from the `.a`, the weak call sees NULL, and the image comes up with no
833/// backend registered (issues 0155 / 0163).
834///
835/// This emits the reference, without naming any backend in nano-ros' own
836/// RMW-agnostic layers — the app crate names it, because the app crate is what
837/// selects an RMW:
838///

840/// #[cfg(feature = "rmw-zenoh")]

842/// #[cfg(feature = "rmw-xrce")]
843/// nros::force_link_backend!(nros_rmw_xrce_cffi);
844/// ```
845///
846/// It is an ANCHOR, not a registration call — the static is never executed
847/// (same class as `nros-c`'s `FORCE_LINK` and `nros-rmw-cffi`'s section anchor).
848/// Registration happens through `nros_app_register_backends`. Backends whose
849/// register entry lives in a C/C++ library the image already links (cyclonedds

851///

853/// expands inside its own anonymous const, so the static names cannot collide.

856    // `ident`, not `path`: a `path` fragment may not be followed by `::`, so
857    // `$backend::register()` fails to parse at the CALL site with a misleading
858    // "expected an operator". Backend crate names are single idents anyway.
859    ($backend:ident) => {
860        const _: () = {
861            #[used]
862            static __NROS_FORCE_LINK_BACKEND: fn() = || {
863                let _ = $backend::register();
864            };
865        };
866    };
867}

996                ::core::option::Option::None => {
997                    $crate::ExecutorConfig::default_const().node_name(<$node as $crate::Node>::NAME)
998                }
999            }
1000            .domain_id(domain_id);
1001            // Issue 0155 — fail LOUD (repo rule: panic, not silent
1002            // early-return). A silent `return` here idles the image with zero
1003            // output; the zephyr-cyclonedds rust lane was undiagnosable until
1004            // this printed the real error.
1005            let executor = match $crate::Executor::open(&config) {
1006                Ok(executor) => executor,
1007                Err(e) => {
1008                    panic!("nros zephyr entry: Executor::open failed: {e:?}");
1009                }
1010            };
1011            let mut runtime = $crate::ExecutorNodeRuntime::from_executor(executor);
1012            if let Err(e) = runtime.register_node::<$node>() {
1013                panic!("nros zephyr entry: register_node failed: {e:?}");
1014            }
1015            // Readiness marker. The C/C++ Zephyr listeners print
1016            // "Waiting for messages..." from their `main()` before the spin
1017            // loop; the e2e harness polls for that substring to know the
1018            // subscriber has declared before starting the talker (Phase 89.12).
1019            // The Rust path's spin loop lives in this macro (the node only owns
1020            // callbacks), so emit the same canonical marker here — without it a
1021            // fully-working Rust listener never signals readiness and the e2e
1022            // times out at 30 s (issue #35: the zenoh native_sim rust pubsub /
1023            // service / action failures were this missing marker, not a
1024            // transport fault — `Executor::open` + `register_node` had already
1025            // succeeded).
1026            ::log::info!("Waiting for messages");
1027            loop {
1028                let _ = runtime.spin_once(::core::time::Duration::from_millis(10));
1029            }
1030        }
1031    };
