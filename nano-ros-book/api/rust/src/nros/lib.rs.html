1//! # nros
2//!
3//! A lightweight ROS 2 client library for embedded systems.
4//!
5//! This crate provides a unified API for building ROS 2 nodes in Rust,
6//! with support for `no_std` environments and embedded targets.
7//!
8//! ## Features
9//!
10//! - **no_std compatible**: Works on bare-metal and RTOS targets
11//! - **Zero-copy where possible**: Minimizes memory allocations
12//! - **Type-safe**: Compile-time verification of message types
13//! - **ROS 2 compatible**: Interoperates with standard ROS 2 nodes via rmw_zenoh
14//!
15//! ## Quick Start
16//!
17//! ```ignore
18//! use nros::prelude::*;
19//! use std_msgs::msg::Int32;
20//!
21//! let config = ExecutorConfig::from_env().node_name("my_node");
22//! let mut executor = Executor::open(&config)?;
23//!
24//! let node = executor.node_builder("my_node").build()?;
25//! let publisher = executor.node_mut(node).create_publisher::<Int32>("/my_topic")?;
26//! publisher.publish(&Int32 { data: 42 })?;
27//!
28//! executor.node_mut(node).create_subscription::<Int32, _>("/topic", |msg: &Int32| {
29//!     println!("Received: {}", msg.data);
30//! })?;
31//!
32//! executor.spin_blocking(SpinOptions::default());
33//! ```
34//!
35//! ## Executor Sizing
36//!
37//! The executor's static memory layout is controlled via environment variables
38//! at build time:
39//!
40//! - **`NROS_EXECUTOR_MAX_CBS`** (default 4) — maximum number of registered
41//!   callbacks (subscriptions + timers + services + guard conditions).
42//! - **`NROS_EXECUTOR_ARENA_SIZE`** (default 4096) — byte budget for storing
43//!   callback closures inline.
44//!
45//! For messages larger than the default 1024-byte receive buffer, size the
46//! subscription via the builder's `.rx_buffer::<N>()` knob (e.g.
47//! `node_mut(id).subscription(t).typed::<M>().rx_buffer::<4096>().build(cb)`).
48//!
49//! ## Transport Backends
50//!
51//! Phase 248 C5c — `nros` is RMW- and platform-AGNOSTIC. It carries only the
52//! `rmw-cffi` vtable; the concrete backend (zenoh / xrce / cyclonedds) enters
53//! the link graph via the board crate (embedded), the board-less app's own
54//! `nros-rmw-*` dep (native), or the `nros-c`/`nros-cpp` staticlib root (D3),
55//! and self-registers through the `RMW_INIT_ENTRIES` walker at `Executor::open`.
56//! The concrete session type is resolved automatically; advanced users can
57//! access it via `nros::internals::RmwSession`.
58//!
59//! ## Crate Features
60//!
61//! `nros` exposes only FUNCTIONAL features — `std`/`alloc`, the `rmw-cffi`
62//! vtable, `lending`, `bridge`/`config`, `param-services`,
63//! `lifecycle-services`, `safety-e2e`, `stream`, `ffi-sync`, and the ROS
64//! edition (`ros-humble`/`ros-iron`). There are NO `platform-*` or concrete
65//! `rmw-*` selector features (Phase 248 C7). Platform + RMW are selected by the
66//! board / staticlib root via dependencies, not `nros` features. The
67//! `zephyr_component_main!` entry macro is gated only on `rmw-cffi` (it's
68//! framework entry codegen, like `nros::main!`), not a platform feature.
69//!
70//! **ROS edition** (select one; RFC-0056 — the per-distro interop profile):
71//! - `ros-humble` - ROS 2 Humble (default; `TypeHashNotSupported`, XCDR1)
72//! - `ros-iron` - ROS 2 Iron (RIHS01 type hash)
73//! - `ros-jazzy` - ROS 2 Jazzy (RIHS01; XCDR2/appendable is phase-303)
74//!
75//! **Other**:
76//! - `std` (default) - Enable standard library support
77//! - `alloc` - Enable heap allocation without full std
78//!
79//! ## Further Reading
80//!
81//! - [`guide`] — tutorials: getting started, services, configuration,
82//!   ROS 2 interop, and troubleshooting
83//! - [Message Generation](https://github.com/jerry73204/nano-ros/blob/main/docs/guides/message-generation.md)
84//!   — codegen reference (all options, output structure, bundled interfaces)

354/// Route this image's panics to its platform — phase-366 W5.c / RFC-0077.
355///
356/// Emits the `#[panic_handler]` for an embedded image, forwarding the message
357/// to `nros_platform_panic` so a Rust panic ends the same way a C precondition
358/// failure or a C++ terminate does. What that ending IS belongs to the port:
359/// `k_panic()` on Zephyr, `esp_system_abort()` on ESP-IDF, UART-then-exit-QEMU
360/// on the ThreadX RV64 board.
361///
362/// # Why this is a macro you INVOKE, not something `nros::main!` emits
363///
364/// `#[panic_handler]` is a singleton of the final artifact, and the image owns
365/// it. Emitting one silently from `nros::main!()` would collide with every image
366/// that already declares its own — `examples/qemu-esp32-baremetal` writes
367/// `use esp_backtrace as _;`, and `logging-smoke-freertos-mps2` uses
368/// `panic-semihosting` with `features = ["exit"]` so a panic exits QEMU instead
369/// of hanging the test harness. Those images are RIGHT, and an invisible default
370/// would fight them.
371///
372/// So the line is written in the entry, where it can be read, swapped for
373/// `use panic_halt as _;`, or replaced by a hand-written handler that logs to
374/// NVM and reboots. A default you cannot see is a constraint, not a default.
375///
376/// # Use — `main!(panic = …)` is the normal way; this is the escape hatch
377///
378/// phase-366 R3. An entry that goes through `nros::main!()` should say
379/// `panic = "platform"` (or nothing — that is the default since M5) and let the
380/// macro emit this body. One line, and the build can check it.
381///
382/// ```ignore
383/// #![no_std]
384/// nros::main!();            // ends through `nros_platform_panic`
385/// ```
386///
387/// Invoke this macro directly only where no `main!()` expansion can carry the
388/// item — a hand-rolled `no_std` binary, or the lib side of a crate whose
389/// `crate-type` includes `staticlib` and whose entry macro is
390/// `zephyr_component_main!` / a board `app_main!`. It is kept for exactly those:
391/// deleting it would strand the images that cannot use the macro replacing it.
392///
393/// ```ignore
394/// // src/app_main.rs — the .a is a final artifact to rustc, and `main!()` in
395/// // the bin target never reaches it.
396/// nros::panic_to_platform!();
397/// ```
398///
399/// Do NOT invoke it in a `std` image: libstd supplies the lang item there and a
400/// second one does not compile. Do not invoke it alongside `use panic_halt as _`
401/// or any other provider, for the same reason — that is the duplicate
402/// `check-archive-lang-items` exists to catch.
403/// Park the core on panic — the `halt` value of `nros::main!(panic = …)`.
404///
405/// For an image that must not print: no formatting, no allocation, no call out
406/// to the platform. Interrupts are masked first so the parked core cannot be
407/// woken back into a half-dead system by a timer or a driver ISR still armed
408/// from before the panic.
409///
410/// This is a body rather than a re-export of the `panic-halt` crate so that
411/// choosing it costs the entry no new dependency — `main!(panic = "halt")` is a
412/// word in a macro the crate already calls, which is the point of the surface.
413/// The behaviour is the same: mask, then spin forever.
414///
415/// Prefer `panic = "platform"`. Halting discards the diagnosis, and every port
416/// implements `nros_platform_panic` precisely so a dying image can say why.
417#[macro_export]
418macro_rules! panic_halt {
419    () => {
420        #[panic_handler]
421        fn __nros_panic_halt(_info: &::core::panic::PanicInfo) -> ! {
422            // Mask interrupts through the platform's critical section, which is
423            // the one IRQ primitive that is portable across the ports (the
424            // `cortex_m`/`riscv` intrinsics are not). Entering and never
425            // leaving is deliberate.
426            unsafe extern "C" {
427                fn nros_platform_critical_section_acquire() -> u32;
428            }
429            // SAFETY: the ABI's acquire takes no argument and returns a restore
430            // token we deliberately drop — nothing after this point runs.
431            unsafe {
432                let _ = nros_platform_critical_section_acquire();
433            }
434            loop {
435                ::core::hint::spin_loop();
436            }
437        }
438    };
439}

441#[macro_export]
442macro_rules! panic_to_platform {
443    () => {
444        #[panic_handler]
445        fn __nros_panic(info: &::core::panic::PanicInfo) -> ! {
446            use ::core::fmt::Write as _;
447
448            // Fixed buffer, never the heap: this runs when the allocator may be
449            // exactly what failed. Truncation is deliberate — a short panic line
450            // still diagnoses; a missing one does not.
451            struct Buf {
452                bytes: [u8; 192],
453                used: usize,
454            }
455            impl ::core::fmt::Write for Buf {
456                fn write_str(&mut self, s: &str) -> ::core::fmt::Result {
457                    let room = self.bytes.len() - self.used;
458                    let n = s.len().min(room);
459                    self.bytes[self.used..self.used + n].copy_from_slice(&s.as_bytes()[..n]);
460                    self.used += n;
461                    Ok(())
462                }
463            }
464
465            let mut buf = Buf {
466                bytes: [0u8; 192],
467                used: 0,
468            };
469            let _ = write!(buf, "{info}");
470
471            unsafe extern "C" {
472                fn nros_platform_panic(msg: *const u8, len: usize) -> !;
473            }
474            // SAFETY: `buf.bytes[..used]` is initialised and outlives the
475            // diverging call; the ABI takes a length-delimited diagnostic, not
476            // a C string.
477            unsafe { nros_platform_panic(buf.bytes.as_ptr(), buf.used) }
478        }
479    };
480}

482/// Define Zephyr's `rust_main` for a self-bringup Rust component package.
483///
484/// The macro is intended for `rust_cargo_application()` apps whose crate
485/// already invokes `nros::node!()`. It opens a Zephyr executor, registers
486/// the supplied component through [`ExecutorNodeRuntime`], and spins forever.
487/// Issue 0330 — force-link an RMW backend crate into a pure-Rust staticlib.
488///
489/// On a Rust-only image (Zephyr and friends) the Zephyr module emits a weak
490/// `nros_rmw_<name>_register` and calls it only if it resolves. The strong
491/// definition is the backend crate's `#[no_mangle]` export — and rustc's
492/// staticlib DCE drops it unless something in the crate being compiled into the
493/// staticlib references that crate. The symbol is then present in the rlib and
494/// absent from the `.a`, the weak call sees NULL, and the image comes up with no
495/// backend registered (issues 0155 / 0163).
496///
497/// This emits the reference, without naming any backend in nano-ros' own
498/// RMW-agnostic layers — the app crate names it, because the app crate is what
499/// selects an RMW:
500///
501/// ```ignore
502/// #[cfg(feature = "rmw-zenoh")]
503/// nros::force_link_backend!(nros_rmw_zenoh);
504/// #[cfg(feature = "rmw-xrce")]
505/// nros::force_link_backend!(nros_rmw_xrce_cffi);
506/// ```
507///
508/// It is an ANCHOR, not a registration call — the static is never executed
509/// (same class as `nros-c`'s `FORCE_LINK` and `nros-rmw-cffi`'s section anchor).
510/// Registration happens through `nros_app_register_backends`. Backends whose
511/// register entry lives in a C/C++ library the image already links (cyclonedds
512/// on Zephyr) need no anchor at all.
513///
514/// Invoke at module scope. Multiple invocations in one crate are fine — each
515/// expands inside its own anonymous const, so the static names cannot collide.
516#[macro_export]
517macro_rules! force_link_backend {
518    // `ident`, not `path`: a `path` fragment may not be followed by `::`, so
519    // `$backend::register()` fails to parse at the CALL site with a misleading
520    // "expected an operator". Backend crate names are single idents anyway.
521    ($backend:ident) => {
522        const _: () = {
523            #[used]
524            static __NROS_FORCE_LINK_BACKEND: fn() = || {
525                let _ = $backend::register();
526            };
527        };
528    };
529}

533// `nros::main!`'s zephyr `rust_main` codegen) — `#[macro_export]` so it emits
534// nothing unless a Zephyr example invokes it; the body's `::zephyr::*` /
535// `::nros_platform::zephyr::wait_network` resolve only in that zephyr-build
536// context (the example deps the `zephyr` crate + `nros-platform[platform-zephyr]`).
537#[cfg(feature = "rmw-cffi")]
538#[macro_export]
539macro_rules! zephyr_component_main {
540    ($node:ty) => {
541        #[unsafe(no_mangle)]
542        pub extern "C" fn rust_main() {
543            unsafe {
544                zephyr::set_logger().ok();
545            }
546            // Phase 248 C7 step 1 — relocated helper (was `$crate::platform::zephyr`).
547            let _ = ::nros_platform::zephyr::wait_network(2000);
548            // Phase 249 P1 — RMW register is board/platform-owned (Phase 248 C5a);
549            // the backend-agnostic `nros` crate cannot register (no backend dep).
550            // Issue 0155 — the "board/platform boot path" that was supposed to
551            // register never fired for pure-Rust Zephyr images: the zephyr
552            // module emits a STRONG `nros_app_register_backends` stub for the
553            // Kconfig-selected RMW (zephyr/CMakeLists.txt Phase 160.A), but
554            // only the C/C++ `nros_cpp_init` path ever CALLED it — a Rust-only
555            // image reached `Executor::open` with no backend registered and
556            // died with Transport(ConnectionFailed) (silently, pre-0155).
557            // Call the hook explicitly, exactly like the C++ init path.
558            unsafe extern "C" {
559                fn nros_app_register_backends();
560            }
561            unsafe { nros_app_register_backends() };
562            // Issue 0163 — a pure-Rust image has no `libnros_c.a`, so the
563            // backend must ride in THIS staticlib and be referenced from the
564            // app crate, or rustc's staticlib DCE drops the whole backend
565            // closure (the `#[no_mangle]` C export included), leaving the
566            // module's weak `nros_rmw_<x>_register` resolving to NULL and the
567            // hook above registering nothing.
568            //
569            // Issue 0330 — that reference used to be a pair of hardcoded
570            // `::nros_rmw_zenoh::register()` / `::nros_rmw_xrce_cffi::register()`
571            // calls emitted RIGHT HERE, which named two concrete backends in
572            // the RMW-agnostic facade (and left cyclonedds handled asymmetrically
573            // through the C hook). It also forced every consumer to carry
574            // `rmw-zenoh` / `rmw-xrce` feature rows purely so these `cfg`s would
575            // resolve — the cyclonedds-only example carried both as inert
576            // placeholders. The anchor now lives in the app crate, which is the
577            // layer that legitimately selects an RMW: see
578            // [`nros::force_link_backend!`]. Registration itself is unchanged —
579            // the `nros_app_register_backends` hook above does it.
580            // Locator: `default_const()` = EMPTY locator → zenoh-pico
581            // multicast scouting, which native_sim NSOS can't satisfy.
582            // Bake `NROS_LOCATOR` at compile time (the example `build.rs`
583            // re-exports `CONFIG_NROS_ZENOH_LOCATOR` from Kconfig into that
584            // env). No baked value → falls back to the empty locator.
585            const BAKED_LOCATOR: ::core::option::Option<&str> = ::core::option_env!("NROS_LOCATOR");
586            // Domain: the example `build.rs` bakes `CONFIG_NROS_DOMAIN_ID`
587            // into `NROS_DOMAIN_ID` the same way (its comment has promised
588            // this consumption since phase-225; the phase-277 macro rework
589            // dropped it — issue 0161: every Rust cyclonedds image silently
590            // ran domain 0 regardless of the Kconfig bake).
591            const BAKED_DOMAIN: ::core::option::Option<&str> =
592                ::core::option_env!("NROS_DOMAIN_ID");
593            let domain_id: u32 = match BAKED_DOMAIN {
594                ::core::option::Option::Some(d) => match d.parse() {
595                    ::core::result::Result::Ok(v) => v,
596                    ::core::result::Result::Err(_) => {
597                        panic!("nros zephyr entry: NROS_DOMAIN_ID baked non-numeric: {d:?}")
598                    }
599                },
600                ::core::option::Option::None => 0,
601            };
602            // #166 / phase-286 W1 — native_sim test parallelism. The test
603            // harness launches the image with `-testargs --nros-locator=<loc>`
604            // and starts a per-test zenohd on that (ephemeral) port; preferring
605            // it over the build-time bake lets every test dial a DISTINCT router,
606            // retiring the shared-baked-port serialization of the zenoh e2e
607            // lanes. Provided by `nros-platform-zephyr` (argv-backed, process
608            // lifetime); returns NULL on real embedded → the bake stands.
609            unsafe extern "C" {
610                fn nros_runtime_locator_override() -> *const ::core::ffi::c_char;
611            }
612            let runtime_locator: ::core::option::Option<&str> = {
613                let p = unsafe { nros_runtime_locator_override() };
614                if p.is_null() {
615                    ::core::option::Option::None
616                } else {
617                    match unsafe { ::core::ffi::CStr::from_ptr(p) }.to_str() {
618                        ::core::result::Result::Ok(s) if !s.is_empty() => {
619                            ::core::option::Option::Some(s)
620                        }
621                        _ => ::core::option::Option::None,
622                    }
623                }
624            };
625            let effective_locator = runtime_locator.or(match BAKED_LOCATOR {
626                ::core::option::Option::Some(loc) if !loc.is_empty() => {
627                    ::core::option::Option::Some(loc)
628                }
629                _ => ::core::option::Option::None,
630            });
631            let config = match effective_locator {
632                ::core::option::Option::Some(loc) => {
633                    $crate::ExecutorConfig::new(loc).node_name(<$node as $crate::Node>::NAME)
634                }
635                ::core::option::Option::None => {
636                    $crate::ExecutorConfig::default_const().node_name(<$node as $crate::Node>::NAME)
637                }
638            }
639            .domain_id(domain_id);
640            // Issue 0155 — fail LOUD (repo rule: panic, not silent
641            // early-return). A silent `return` here idles the image with zero
642            // output; the zephyr-cyclonedds rust lane was undiagnosable until
643            // this printed the real error.
644            let executor = match $crate::Executor::open(&config) {
645                Ok(executor) => executor,
646                Err(e) => {
647                    panic!("nros zephyr entry: Executor::open failed: {e:?}");
648                }
649            };
650            let mut runtime = $crate::ExecutorNodeRuntime::from_executor(executor);
651            if let Err(e) = runtime.register_node::<$node>() {
652                panic!("nros zephyr entry: register_node failed: {e:?}");
653            }
654            // Readiness marker. The C/C++ Zephyr listeners print
655            // "Waiting for messages..." from their `main()` before the spin
656            // loop; the e2e harness polls for that substring to know the
657            // subscriber has declared before starting the talker (Phase 89.12).
658            // The Rust path's spin loop lives in this macro (the node only owns
659            // callbacks), so emit the same canonical marker here — without it a
660            // fully-working Rust listener never signals readiness and the e2e
661            // times out at 30 s (issue #35: the zenoh native_sim rust pubsub /
662            // service / action failures were this missing marker, not a
663            // transport fault — `Executor::open` + `register_node` had already
664            // succeeded).
665            ::log::info!("Waiting for messages");
666            loop {
667                let _ = runtime.spin_once(::core::time::Duration::from_millis(10));
668            }
669        }
670    };
671}

784    /// Used by the C API (`nros-c`); Rust users should prefer `Executor::open()`.
785    ///
786    /// Phase 156 — consults `$NROS_RMW` (when std + the env var is set)
787    /// to pin the primary backend by name, mirroring what `Executor::open`
788    /// does for Rust callers. Without this, C bridges built with two

790    /// first via linkme — non-deterministic across link orderings +
791    /// often the wrong backend for the bridge's intended primary.

794        locator: &str,
795        mode: nros_rmw::SessionMode,
796        domain_id: u32,
797        node_name: &str,
798    ) -> Result<RmwSession, nros_rmw::TransportError> {

801        // Phase 249 P4b.1 — every linked backend self-registered via
802        // its `.init_array` ctor before `main` (RFC-0042 §D3.3); no
803        // runtime section walk.
804
805        let config = nros_rmw::RmwConfig {
806            locator,
807            mode,
808            domain_id,
809            node_name,
810            namespace: "",
811            properties: &[],
812        };
813        // Phase 156 — honor `$NROS_RMW` env-var primary selector
814        // when present so C bridges built with multiple linked
815        // backends (e.g. xrce + dds) pin the primary deterministically
816        // instead of taking whichever linkme ctor fires first.
817        // Phase 155.B — propagate the real `TransportError` instead of
818        // collapsing every backend failure to `ConnectionFailed`. The
819        // C-side `nros_support_init` decodes the variant into a
820        // specific `NROS_RET_*` code so "init -> -X" tells the user

826        // rather than `config.rmw`: a config the caller assembled by hand has
827        // no selector in it, and this entry point has always honoured the
828        // variable.
829        #[cfg(feature = "env")]
830        if let Some(name) = crate::rmw_selector() {
831            return nros_rmw_cffi::CffiRmw::open_with_rmw(name.as_str(), &config);
832        }
833        nros_rmw_cffi::CffiRmw.open(&config)
834    }

1106// ---------------------------------------------------------------------------
1107// phase-361 W8.e / issue 0594 — capabilities REQUIRE the heap / the standard
1108// library, they do not enable it. Turning `alloc` or `std` on for the user
1109// silently changes what their firmware image is; naming the feature they must
1110// add does not.
1111// ---------------------------------------------------------------------------
1112// issue 0687 follow-up — `alloc`, not `std`. The reason recorded here ("writes
1113// a file and exits") was never this crate's: the file write is `nros-cpp`'s
1114// `metadata_hooks`. What `metadata_mode.rs` actually needed was a `Sync`
1115// global, and it named `std::sync::Mutex` for it; on the portable mutex the
1116// capability is `String` + `format!` + a lock, i.e. the heap and nothing more.
1117#[cfg(all(feature = "metadata-mode", not(feature = "alloc")))]
1118compile_error!(
1119    "`metadata-mode` records into a heap-allocated global: add \"alloc\" to this crate's features"
1120);
1121// Emitted here as well as in `nros-node`, and NOT for the reason it first
1122// looks like. `nros = { features = ["env"] }` alone does not reach this line:
1123// `env` forwards to `nros-node/env`, nros-node is compiled first, and its own
1124// guard aborts the build there — measured, not assumed. What this covers is
1125// the case feature unification creates, where some other crate in the graph
1126// turns `nros-node/std` on so that guard stays quiet while THIS crate's `std`
1127// is still off. Rare, and exactly the shape that would otherwise compile a
1128// hosted capability into a build that never named the standard library.
1129#[cfg(all(feature = "env", not(feature = "std")))]
1130compile_error!(
1131    "`env` reads the process environment, which needs the standard library: add \"std\" to this crate's features"
1132);
