1//! A fixed RAM record the image writes about itself, for targets where no log
2//! sink reaches a human.
3//!
4//! # Why this exists
5//!
6//! phase-412 derived six pool counts and the executor arena for the
7//! mr-canhubk344 island, and then could not tell whether the derived image was
8//! correct. The only available signal was the ROS graph's node count, and one
9//! unchanged configuration produced 4, 0, 0, 4, 4 across five runs. Every other
10//! channel was already disqualified for that board:
11//!
12//! * The console is on `lpuart0`, which is not wired on the MR-CANHUBK344.
13//!   `lpuart2` is the zenoh serial transport and cannot carry a second protocol.
14//! * `nros_log` therefore reaches nothing. Both arena diagnostics (issue 0900)
15//!   go through it, so the two messages written specifically to explain an
16//!   arena failure are invisible on the one board that needed them.
17//! * SEGGER RTT was tried and could not discriminate: a working image and a
18//!   derived image both emitted only the Zephyr banner, and a deliberate
19//!   positive control produced nothing at all.
20//! * Semihosting halts the core until a probe answers and FAULTS with no probe
21//!   attached, so an image carrying it cannot run standalone.
22//!
23//! What all of those share is that they are STREAMS: they need the board to
24//! still be running, and they need somebody attached at the moment the
25//! interesting thing happens. The failure this campaign is trying to see is the
26//! opposite shape. An under-sized arena halts DURING entity creation, before
27//! the first spin, so issue 0900's advisory never prints -- the failure cannot
28//! report itself through any stream.
29//!
30//! So this is not a stream. It is a fixed-size record in RAM that the image
31//! keeps up to date as it boots, read out AFTERWARDS by halting the core and
32//! dumping memory. It survives the halt because it does not depend on anything
33//! still running, and a PARTIAL record is the useful case rather than a lost
34//! one: the last stage reached and the allocation that did not fit are exactly
35//! what names the knob to change.
36//!
37//! # Reading it
38//!
39//! The record is a `#[no_mangle]` static, so it has a symbol in the ELF and a
40//! debugger can find it without the address being wired in anywhere:
41//!
42//! ```text
43//! pyocd commander -t s32k344 -c "halt" -c "savemem <addr> <len> report.bin"
44//! python3 scripts/read-boot-report.py <elf> report.bin
45//! ```
46//!
47//! [`MAGIC`] distinguishes a written record from uninitialised RAM, and
48//! [`BootReport::struct_size`] lets a reader refuse a layout it does not know
49//! rather than decode it wrongly.
50//!
51//! # Cost, and why it is opt-in
52//!
53//! Enabled by setting `NROS_BOOT_REPORT=1` at build time (Zephyr:
54//! `CONFIG_NROS_BOOT_REPORT=y`), which makes `nros-node`'s build script emit
55//! `cfg(nros_boot_report)`. With the cfg absent every function here is an empty
56//! `#[inline(always)]` body and the static does not exist, so an image that
57//! does not opt in is byte-identical to one built before this module -- the
58//! same rule issue 0900's arena knob and phase-403's `rx_buffer_from_type()`
59//! both keep.
60//!
61//! Enabled, it costs [`BootReport::struct_size`] bytes of `.bss` -- 88, the
62//! same on every target because every field is a `u32` -- and a handful of
63//! relaxed atomic stores on paths that run once per entity at registration.
64//!
65//! The 88 is not a detail: it is the LENGTH an operator types into `savemem`,
66//! and this sentence said 60 for as long as the record had fifteen fields. A
67//! short dump decodes -- `read-boot-report.py` needs `22 * 4` bytes and a
68//! 60-byte one is refused, but a reader who trusts the prose over the tool
69//! spends the refusal looking at the wrong thing. Ask the tool instead:
70//! `read-boot-report.py --addr-only <elf>` prints the address AND the length,
71//! from the ELF's own symbol size.
72//!
73//! # Adding a field (phase-460 W5, for W7 and after)
74//!
75//! The record is meant to grow, and the order it grows in is the whole
76//! contract: `read-boot-report.py` decodes POSITIONALLY. So a new field is
77//! APPENDED -- after the last field, never inserted between two -- and the
78//! four edits are one commit:
79//!
80//! 1. the field on [`BootReport`], its zero in `BootReport::new`, the same
81//!    name in the same position on [`Snapshot`], and its load in [`snapshot`];
82//! 2. [`VERSION`] bumped, so an older decoder REFUSES the record instead of
83//!    reading the new word as one it knows;
84//! 3. `FIELDS` in `scripts/read-boot-report.py`, same name, same position, and
85//!    `KNOWN_VERSION` to match;
86//! 4. the field count in `the_record_is_twenty_two_packed_u32s` below.
87//!
88//! `check-boot-report-layout` fails on 1 without 3, and the Rust test fails if
89//! the compiler laid the record out with padding. Appending is what keeps a
90//! dump taken from an older image decodable by eye: every word before the new
91//! one is still where it was, and the version says which words exist.

95/// `"NRSR"` -- nano-ros self report. Written LAST, so a reader that finds it
96/// knows every field before it is already valid.
97pub const MAGIC: u32 = 0x4e52_5352;
98
99/// Layout version. Bump on any field change; a reader refuses what it does not
100/// know rather than decoding a record it would misread.
101///
102/// 4 since phase-460 W5 appended `heap_peak_bytes` and `heap_capacity_bytes`.
103pub const VERSION: u32 = 4;
104
105/// How far boot got. Monotonic, and the single most useful field: an arena
106/// failure halts during entity creation, so the stage that was NOT reached
107/// names the phase to look at.
108///
109/// Numbers follow EXECUTION ORDER, because `checkpoint` keeps the maximum
110/// and a stage that runs earlier but numbers higher would make the record
111/// claim less progress than was made. Inserting one therefore renumbers the
112/// rest and bumps [`VERSION`]; the decoder refuses a version it does not
113/// know rather than misreading it, which is what makes that safe.
114#[derive(Clone, Copy, PartialEq, Eq, Debug)]
115#[repr(u32)]
116pub enum Stage {
117    /// RAM as the loader left it. Never stored; a reader seeing this with a
118    /// valid magic has found a record that was reset but not re-entered.
119    Untouched = 0,
120    /// The record itself is initialised and the compile-time knobs are in it.
121    ///
122    /// Stamped at the TOP of the C++ entry point, before any argument is
123    /// validated, so "the image never entered nano-ros" is distinguishable
124    /// from "it entered and died before the executor". Version 1 stamped this
125    /// inside the executor constructor instead, which made those two cases
126    /// identical -- both read magic 0 -- and cost a disassembly walk to tell
127    /// apart on the first board run.
128    ReportReady = 1,
129    /// The boot config resolved: node name, namespace, locator and domain id
130    /// all parsed. Everything between here and [`Stage::ReportReady`] is
131    /// argument validation, and [`BootReport::cpp_init_ret`] says which check
132    /// rejected it.
133    BootConfigResolved = 2,
134    /// An `Executor` has bound its arena, so [`BootReport::arena_capacity`]
135    /// is the real slice length rather than the compiled constant.
136    ExecutorReady = 3,
137    /// Entity registration has begun: something claimed arena bytes.
138    ///
139    /// Stamped by [`note_alloc`] and [`note_alloc_failed`], which is to say by
140    /// the arena allocator itself rather than by any register seam. The arena
141    /// is claimed by entity registration and by nothing else, so an allocation
142    /// ATTEMPT is the event, and putting the stamp on the record's own writers
143    /// means every present and future `arena_alloc*` call site is covered by
144    /// construction -- there is no second place to remember.
145    ///
146    /// Issue 1036: nothing emitted this for three phases, so an image that ran
147    /// out of arena left the stage reading [`Stage::ExecutorReady`] -- the same
148    /// value as an image that opened its executor and died before registering
149    /// anything at all. The record named the allocation and could not say
150    /// WHERE, which is half of a diagnostic on a board where it is the only
151    /// channel.
152    ///
153    /// The interval between this and [`Stage::FirstSpin`] is where an
154    /// under-sized arena halts, so `stage == 4` with a non-zero
155    /// [`BootReport::failed_alloc_shortfall`] is the signature of the failure
156    /// this whole record exists to catch.
157    RegisteringEntities = 4,
158    /// RESERVED. Nothing emits this, and nothing can from inside the core.
159    ///
160    /// "Every entity the image declares was registered successfully" has no
161    /// observable moment here: an application may register lazily, which is the
162    /// same reason issue 0900's headroom advisory fires at the first spin
163    /// rather than at an end of registration that does not exist. A stamp at
164    /// the top of `spin_once` would be a claim the core cannot support.
165    ///
166    /// Kept rather than removed, and DOCUMENTED rather than left looking
167    /// unfinished (issue 1036): removing it renumbers [`Stage::FirstSpin`] and
168    /// bumps [`VERSION`] to retire a value no image can produce, and the next
169    /// reader would file the renumbering as the bug. An entry shape that DOES
170    /// know when its register pass ended -- a generated component `setup`
171    /// callback returning OK -- can stamp it without moving anything.
172    EntitiesReady = 5,
173    /// The first `spin_once` was entered, which is where issue 0900's
174    /// headroom advisory would have printed had a sink existed.
175    ///
176    /// Because [`Stage::EntitiesReady`] has no producer, this is also what
177    /// "registration finished" reads as: reaching 6 means the application
178    /// stopped registering and started spinning.
179    FirstSpin = 6,
180}

190    /// The record. One per image, in `.bss`.
191    ///
192    /// `#[repr(C)]` with every field an `AtomicU32` -- which is
193    /// `repr(transparent)` over `u32` -- so the layout is exactly the sequence
194    /// of 32-bit words the reader script decodes, on every target this crate
195    /// builds for.
196    ///
197    /// Atomics rather than a `static mut` because the record is written from
198    /// registration paths that an application may reach from more than one
199    /// thread. `Relaxed` throughout: there is no ordering relationship to
200    /// establish with any other data, and the reader is a debugger that has
201    /// already halted the core.
202    #[repr(C)]
203    pub struct BootReport {
204        magic: AtomicU32,
205        version: AtomicU32,
206        struct_size: AtomicU32,
207        stage: AtomicU32,
208
209        // Compile-time, so that comparing these against what the build system
210        // BELIEVES it delivered turns a "derived value did not arrive" defect
211        // into a measurement. `scripts/check-knob-delivery.py` asserts the same
212        // identity one step earlier, at `build.ninja`; this is the same
213        // assertion made by the silicon.
214        arena_size: AtomicU32,
215        max_cbs: AtomicU32,
216        max_sc: AtomicU32,
217        max_nodes: AtomicU32,
218        default_rx_buf_size: AtomicU32,
219
220        // Runtime.
221        arena_capacity: AtomicU32,
222        arena_used: AtomicU32,
223        alloc_count: AtomicU32,
224        last_alloc_size: AtomicU32,
225        /// Bytes the allocation that FAILED asked for, or 0 if none has.
226        failed_alloc_size: AtomicU32,
227        /// Bytes by which that allocation overran the arena. This is the
228        /// number to add to `NROS_EXECUTOR_ARENA_SIZE`, which is why it is
229        /// stored rather than left to be recomputed from the two above.
230        failed_alloc_shortfall: AtomicU32,
231        /// `nros_cpp_init`'s return code, as the two's-complement bits of an
232        /// `i32`, or 0 (`NROS_CPP_RET_OK`) if it has not returned yet.
233        ///
234        /// The stage says HOW FAR init got; this says why it stopped. Without
235        /// it, every early return in that function -- a null argument, a
236        /// non-UTF-8 name, a bad domain id, a backend that refused to open --
237        /// is one indistinguishable "did not reach the executor".
238        cpp_init_ret: AtomicU32,
239        /// The LAST `NodeError` that crossed the C++ FFI, as a stable code.
240        ///
241        /// Stable here means assigned by `nros-cpp`'s exhaustive mapper, not
242        /// taken from the Rust discriminant -- a discriminant shifts whenever a
243        /// variant is inserted, and a dump decoded against the wrong numbering
244        /// names the wrong error, confidently.
245        err_class: AtomicU32,
246        /// For [`Self::err_class`] == Transport, which `TransportError`.
247        ///
248        /// The C++ ABI collapses eight distinct transport variants onto the
249        /// single code -100, which is what made an island subscription failure
250        /// undiagnosable: the return code said "transport" and nothing said
251        /// which. This is the field that separates them.
252        err_transport: AtomicU32,
253        /// Address of the `Backend(&'static str)` message, or 0.
254        ///
255        /// The pointer rather than the text: the message is a static string
256        /// already in the image, so copying it would cost the record a buffer
257        /// to hold something the reader can fetch. Paired with
258        /// [`Self::err_backend_len`].
259        err_backend_ptr: AtomicU32,
260        /// Length of the message at [`Self::err_backend_ptr`], or 0.
261        err_backend_len: AtomicU32,
262
263        // The platform heap -- the arena `nros_platform_alloc` hands out of,
264        // which on Zephyr is CONFIG_NROS_ZEPHYR_HEAP_SIZE. Appended by
265        // phase-460 W5; see "Adding a field" above for why the two words are
266        // at the END.
267        /// High-water mark of the platform heap, in bytes, or 0 if this image
268        /// never sampled it.
269        ///
270        /// `peak`, not `used`: `used` read at an arbitrary instant reports
271        /// whatever happened to be live at the moment of the read, which is
272        /// not what a size knob bounds. Issue 1424 -- the reporter behind this
273        /// (`nros_zephyr_heap_peak`) has existed and been compiled into every
274        /// Zephyr image since phase-412, and nothing read it off a board with
275        /// no console, so the one knob it could have sized
276        /// (`CONFIG_NROS_ZEPHYR_HEAP_SIZE`) was set by hand and annotated as a
277        /// guess.
278        ///
279        /// MONOTONIC here as well as at the source, so a later sample of a
280        /// heap that has since freed memory cannot lower the figure the knob
281        /// is sized from.
282        heap_peak_bytes: AtomicU32,
283        /// Bytes the platform heap was given, or 0 if never sampled.
284        ///
285        /// The pair is what makes the peak actionable: a peak alone says how
286        /// much was needed and says nothing about how close to the edge the
287        /// image ran. `capacity - peak` is the headroom the gate refuses on.
288        heap_capacity_bytes: AtomicU32,
289    }

319        /// Size of the record in bytes, as the reader must expect it.
320        ///
321        /// ASKED OF THE COMPILER, not counted by hand. A hand-written word
322        /// count is a second statement of the field list that drifts the first
323        /// time a field is added, and it would drift SILENTLY -- the reader
324        /// would accept the record and decode one field short. This whole
325        /// campaign is about not hand-picking numbers the build already knows.
326        #[must_use]
327        pub const fn struct_size() -> u32 {
328            // The record is all `AtomicU32`, so this is exact on every target
329            // and there is no padding for the cast to lose.
330            core::mem::size_of::<Self>() as u32
331        }
332    }

397    /// The record, findable by symbol name from a debugger.
398    ///
399    /// `#[used]` because nothing in a minimal image necessarily reads it, and a
400    /// static whose only writes are through this module's functions is exactly
401    /// what a linker is entitled to discard.
402    #[unsafe(no_mangle)]
403    #[used]
404    pub static NROS_BOOT_REPORT: BootReport = BootReport::new();

406    /// Stamp the header and the compile-time knobs.
407    ///
408    /// Idempotent, and safe to call from more than one place -- an image with
409    /// two executors should not have to decide which one owns the record.
410    /// MAGIC is stored LAST so a reader that finds it knows the rest is there.
411    pub fn init() {
412        let r = &NROS_BOOT_REPORT;
413        r.version.store(VERSION, Ordering::Relaxed);
414        r.struct_size
415            .store(BootReport::struct_size(), Ordering::Relaxed);
416        r.arena_size
417            .store(saturate(crate::config::ARENA_SIZE), Ordering::Relaxed);
418        r.max_cbs
419            .store(saturate(crate::config::MAX_CBS), Ordering::Relaxed);
420        r.max_sc
421            .store(saturate(crate::config::MAX_SC), Ordering::Relaxed);
422        r.max_nodes
423            .store(saturate(crate::config::MAX_NODES), Ordering::Relaxed);
424        r.default_rx_buf_size.store(
425            saturate(crate::config::DEFAULT_RX_BUF_SIZE),
426            Ordering::Relaxed,
427        );
428        r.magic.store(MAGIC, Ordering::Relaxed);
429        checkpoint(Stage::ReportReady);
430    }

432    /// Record that boot reached `stage`.
433    ///
434    /// MONOTONIC: a lower stage never overwrites a higher one, so a late call
435    /// on a re-entered path cannot make the record claim less progress than was
436    /// actually made. That matters because the field's whole purpose is to be
437    /// believed about a boot that did not finish.
438    pub fn checkpoint(stage: Stage) {
439        let want = stage as u32;
440        let r = &NROS_BOOT_REPORT;
441        let mut cur = r.stage.load(Ordering::Relaxed);
442        while want > cur {
443            match r
444                .stage
445                .compare_exchange_weak(cur, want, Ordering::Relaxed, Ordering::Relaxed)
446            {
447                Ok(_) => return,
448                Err(actual) => cur = actual,
449            }
450        }
451    }

453    /// Record the arena slice an `Executor` actually bound.
454    ///
455    /// Not the same number as `ARENA_SIZE`, and the difference is a finding
456    /// rather than noise: the arena's placement is the caller's choice
457    /// (issue 0900), so an image can compile one size and hand the executor
458    /// another. Both are in the record so a dump can say which happened.
459    pub fn note_arena_capacity(capacity: usize) {
460        NROS_BOOT_REPORT
461            .arena_capacity
462            .store(saturate(capacity), Ordering::Relaxed);
463    }

465    /// Record a successful arena allocation.
466    ///
467    /// Also stamps [`Stage::RegisteringEntities`]: see that variant for why the
468    /// stamp belongs to the record's writers rather than to a register seam.
469    pub fn note_alloc(size: usize, used_after: usize) {
470        let r = &NROS_BOOT_REPORT;
471        r.alloc_count.fetch_add(1, Ordering::Relaxed);
472        r.last_alloc_size.store(saturate(size), Ordering::Relaxed);
473        r.arena_used.store(saturate(used_after), Ordering::Relaxed);
474        checkpoint(Stage::RegisteringEntities);
475    }
476
477    /// Record the arena allocation that did not fit.
478    ///
479    /// FIRST writer wins, on the same reasoning as [`checkpoint`]: the first
480    /// failure is the one that explains the boot, and any later one is a
481    /// consequence of it.
482    /// Also stamps [`Stage::RegisteringEntities`], and UNCONDITIONALLY -- outside
483    /// the first-writer branch. A second failure adds nothing to the numbers but
484    /// it is still evidence that registration was in flight, and a stage that
485    /// depended on winning a race would be exactly the sort of number this
486    /// record must never print.
487    pub fn note_alloc_failed(size: usize, shortfall: usize) {
488        let r = &NROS_BOOT_REPORT;
489        checkpoint(Stage::RegisteringEntities);
490        if r.failed_alloc_size
491            .compare_exchange(0, saturate(size), Ordering::Relaxed, Ordering::Relaxed)
492            .is_ok()
493        {
494            r.failed_alloc_shortfall
495                .store(saturate(shortfall), Ordering::Relaxed);
496        }
497    }

499    /// Record `nros_cpp_init`'s return code.
500    ///
501    /// LAST writer wins, unlike [`note_alloc_failed`]: an image may call
502    /// `nros_cpp_init` more than once (per component, per tier), and the
503    /// interesting one is the call that did not get through, which is the one
504    /// that leaves the stage where it stopped.
505    pub fn note_cpp_init_ret(ret: i32) {
506        NROS_BOOT_REPORT
507            .cpp_init_ret
508            .store(ret as u32, Ordering::Relaxed);
509    }

511    /// Record an error that crossed the FFI.
512    ///
513    /// Takes CODES, not the error type: `nros-node` must not need to know how
514    /// `nros-cpp` numbers its variants, and the numbering has to be assigned by
515    /// an exhaustive match that a new variant breaks at compile time. The caller
516    /// owns both.
517    ///
518    /// LAST writer wins. An image that fails one entity and carries on would
519    /// otherwise keep the first stumble instead of the one that stopped it, and
520    /// the failure that stops setup is the one that explains the boot.
521    pub fn note_error(class: u32, transport: u32, backend_ptr: u32, backend_len: u32) {
522        let r = &NROS_BOOT_REPORT;
523        r.err_class.store(class, Ordering::Relaxed);
524        r.err_transport.store(transport, Ordering::Relaxed);
525        r.err_backend_ptr.store(backend_ptr, Ordering::Relaxed);
526        r.err_backend_len.store(backend_len, Ordering::Relaxed);
527    }

529    /// Record the platform heap's high-water mark and its capacity.
530    ///
531    /// `peak` keeps the MAXIMUM, `capacity` the last value: the peak is the
532    /// figure a knob is sized from and must not be lowered by a later sample,
533    /// while the capacity is a constant of the image that a second sample can
534    /// only restate.
535    ///
536    /// Called from the port that owns the heap, because only that port can
537    /// read it: `nros_zephyr_heap_peak()` is deliberately NOT in
538    /// `nros/platform.h` (the cross-port ABI would need a stub per port for a
539    /// figure one port can produce), so the core cannot pull the number and
540    /// the platform pushes it instead. See
541    /// [`nros_boot_report_note_heap`] for the C entry point.
542    pub fn note_heap(peak: usize, capacity: usize) {
543        let r = &NROS_BOOT_REPORT;
544        r.heap_peak_bytes
545            .fetch_max(saturate(peak), Ordering::Relaxed);
546        r.heap_capacity_bytes
547            .store(saturate(capacity), Ordering::Relaxed);
548    }
549
550    /// [`note_heap`] across the C ABI, for a platform written in C.
551    ///
552    /// `nros-platform-zephyr`'s `platform.c` calls this from
553    /// `nros_platform_alloc` and `nros_platform_realloc` -- the only two
554    /// places the heap's peak can change -- so the record is current at every
555    /// stage transition without the stage transitions having to sample
556    /// anything, and it is written on the exhaustion path BEFORE the printk
557    /// that path emits, which is the case where the board is about to stop.
558    ///
559    /// Takes `usize`, not `u32`: the saturation rule belongs on this side
560    /// (see [`saturate`]), and a C caster would truncate instead.
561    #[unsafe(no_mangle)]
562    pub extern "C" fn nros_boot_report_note_heap(peak: usize, capacity: usize) {
563        note_heap(peak, capacity);
564    }
565
566    /// `usize` -> `u32`, saturating.
567    ///
568    /// Every field is a `u32` so the record's layout does not change between a
569    /// 32-bit board and a 64-bit host running the same tests. Saturating rather
570    /// than truncating because a value too large to represent should read as
571    /// "enormous", not as its low half -- a truncated 4 GiB reads as 0, which
572    /// is the one wrong answer that looks like a normal one.
573    fn saturate(v: usize) -> u32 {
574        u32::try_from(v).unwrap_or(u32::MAX)
575    }
576}

622#[cfg(all(test, nros_boot_report))]
623mod tests {
624    use super::*;
625
626    /// The reader decodes twenty-two u32s positionally, so the record must be
627    /// exactly that and nothing else -- no padding, no reordering.
628    ///
629    /// `size_of` on the TARGET, which is the half `check-boot-report-layout.py`
630    /// cannot see: that gate compares two source files, and this compares the
631    /// source against what the compiler actually laid out.
632    #[test]
633    fn the_record_is_twenty_two_packed_u32s() {
634        assert_eq!(BootReport::struct_size(), 22 * 4);
635        assert_eq!(
636            core::mem::size_of::<BootReport>(),
637            22 * core::mem::size_of::<u32>(),
638            "the record grew padding; the reader decodes positionally"
639        );
640        assert_eq!(core::mem::align_of::<BootReport>(), 4);
641    }
642
643    /// The magic is written LAST, so finding it means the rest is valid.
644    ///
645    /// The reader leans on this to tell "the image died before it had an
646    /// executor" apart from "the dump is at the wrong address", and it can
647    /// only do so if the ordering actually holds.
648    #[test]
649    fn init_stamps_the_header_and_the_compiled_knobs() {
650        init();
651        let s = snapshot();
652        assert_eq!(s.magic, MAGIC);
653        assert_eq!(s.version, VERSION);
654        assert_eq!(s.struct_size, BootReport::struct_size());
655        assert_eq!(s.arena_size, crate::config::ARENA_SIZE as u32);
656        assert_eq!(s.max_cbs, crate::config::MAX_CBS as u32);
657        assert_eq!(s.max_nodes, crate::config::MAX_NODES as u32);
658        assert!(s.stage >= Stage::ReportReady as u32);
659    }
660
661    /// A late call on a re-entered path must not make the record claim LESS
662    /// progress than was actually made. The field's whole purpose is to be
663    /// believed about a boot that did not finish.
664    #[test]
665    fn a_checkpoint_never_goes_backwards() {
666        init();
667        checkpoint(Stage::FirstSpin);
668        assert_eq!(snapshot().stage, Stage::FirstSpin as u32);
669        checkpoint(Stage::ExecutorReady);
670        assert_eq!(
671            snapshot().stage,
672            Stage::FirstSpin as u32,
673            "an earlier stage overwrote a later one"
674        );
675    }
676
677    /// The FIRST failure is the one that explains the boot; a later one is a
678    /// consequence of it and must not overwrite the cause.
679    #[test]
680    fn the_first_alloc_failure_wins() {
681        init();
682        note_alloc_failed(100, 8);
683        note_alloc_failed(999, 512);
684        let s = snapshot();
685        assert_eq!(s.failed_alloc_size, 100);
686        assert_eq!(s.failed_alloc_shortfall, 8);
687    }
688
689    /// A value too large for the field must read as enormous, not as its low
690    /// half. A truncated 4 GiB reads as 0, which is the one wrong answer that
691    /// looks like a normal one.
692    #[test]
693    fn an_unrepresentable_size_saturates_rather_than_truncating() {
694        init();
695        note_arena_capacity(usize::MAX);
696        assert_eq!(snapshot().arena_capacity, u32::MAX);
697    }
698
699    /// The heap PEAK is what sizes the knob, so a later sample taken after the
700    /// image freed memory must not lower it. Issue 1424: the figure only has
701    /// to be believed about a boot nobody watched.
702    ///
703    /// Through the C entry point, which is how the only producer in the tree
704    /// (`nros-platform-zephyr/src/platform.c`) reaches it -- a test that wrote
705    /// through `note_heap` would leave that symbol exercised by nothing.
706    #[test]
707    fn the_heap_peak_keeps_the_maximum_and_the_capacity_the_last_word() {
708        init();
709        nros_boot_report_note_heap(4096, 94208);
710        nros_boot_report_note_heap(18352, 94208);
711        nros_boot_report_note_heap(1024, 94208);
712        let s = snapshot();
713        assert_eq!(s.heap_peak_bytes, 18352, "a later sample lowered the peak");
714        assert_eq!(s.heap_capacity_bytes, 94208);
715    }
