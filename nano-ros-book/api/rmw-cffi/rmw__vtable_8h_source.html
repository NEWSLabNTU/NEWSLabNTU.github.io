4/* Phase 376 W3.a — this header defines the GENERIC RMW ABI: its types are
5 * `rmw_publisher_t`, `rmw_ret_t`, and so on, with no vendor prefix, because a
6 * backend author implements RMW rather than nano-ros.
7 *
8 * That makes it impossible to share a translation unit with upstream's
9 * `<rmw/rmw.h>`, which defines the same names differently. Refuse LOUDLY rather
10 * than let one definition silently win a redefinition race — two types of one
11 * name whose layouts disagree is the class this repo has already paid for three
12 * times in hand-mirrored FFI structs.
13 *
14 * A target image never links real rmw, and host-side consumers reach the
15 * backend through Rust, so nothing in this repo trips this today. It exists for
16 * the day something does. */
17#if defined(RMW_RMW_H_) || defined(RMW__RMW_H_)
18#error "nros/rmw_vtable.h defines the generic RMW ABI and cannot share a translation unit with upstream <rmw/rmw.h>. Include one or the other."
19#endif

63/* ---- Phase 376 W4 — graph enumeration visitors ----
64 *
65 * Upstream returns `rcutils_string_array_t` and `rmw_names_and_types_t`, which
66 * ALLOCATE — two levels deep for names-and-types. There is no allocator at this
67 * seam, and a caller-provides-the-buffer shape is worse than it looks: the ROS
68 * graph has no bound the CALLER can know, so a 128 KiB image would have to
69 * reserve permanently for the worst graph it might ever meet, and the backend
70 * would still have to materialise the whole list to fill the buffer.
71 *
72 * So enumeration is a VISITOR. Peak extra RAM is one entry, the backend streams
73 * from state it already holds, and a caller with a bound stops early by
74 * returning `false` — a normal outcome, not a truncation error. Same shape as
75 * `process_raw_in_place` and `publish_streamed` already use here.
76 *
77 * Every string handed to a visitor is BORROWED for that call only.
78 */

830 /* ---- Phase 376 W4 — graph node lifecycle (optional) ----
831 *
832 * The rest of upstream's lifecycle group is deliberately absent, and the
833 * absences are decisions rather than omissions:
834 *
835 * - `rmw_init` / `rmw_shutdown` / `rmw_context_fini` are
836 * `create_session` / `destroy_session`. There is no second teardown
837 * phase: the session shell is caller-owned, so there is nothing left to
838 * free after the backend releases `backend_data`.
839 *
840 * - `rmw_init_options_{init,copy,fini}` have nothing to do here. Upstream
841 * needs the trio because its options OWN heap and carry an
842 * `rcutils_allocator_t`, which cannot cross this seam; ours is a
843 * build-time POD, so "copy" is `=` and "fini" is nothing. (This does NOT
844 * decide `security_options` / `discovery_options`, which we answer
845 * nowhere — see the phase doc.)
846 *
847 * - `rmw_wait`, the wait set, and the guard conditions are declined
848 * together, because `has_data` / `has_request` + `drive_io` +
849 * `set_wake_callback` + `next_deadline_ms` ARE upstream's `rmw_wait`,
850 * decomposed. What a vtable `wait` would add is only the BLOCK, moved
851 * from the platform into the backend — and the block cannot live there:
852 * one executor drives sessions from several backends at once
853 * (`create_node_on(name, rmw)`), timers fire off the platform clock, and
854 * guard conditions fire from another thread or an ISR. A backend can
855 * only block on its own handles. `next_deadline_ms` is exactly the piece
856 * of `rmw_wait` that CANNOT be answered above the seam, and it is
857 * already a slot; that is the decomposition working, not a gap.
858 */
