4/* Phase 376 W3.a — this header defines the GENERIC RMW ABI: its types are
5 * `rmw_publisher_t`, `rmw_ret_t`, and so on, with no vendor prefix, because a
6 * backend author implements RMW rather than nano-ros.
7 *
8 * That makes it impossible to share a translation unit with upstream's
9 * `<rmw/rmw.h>`, which defines the same names differently. Refuse LOUDLY rather
10 * than let one definition silently win a redefinition race — two types of one
11 * name whose layouts disagree is the class this repo has already paid for three
12 * times in hand-mirrored FFI structs.
13 *
14 * A target image never links real rmw, and host-side consumers reach the
15 * backend through Rust, so nothing in this repo trips this today. It exists for
16 * the day something does. */

78/* ---- Phase 376 W4 — graph enumeration visitors ----
79 *
80 * Upstream returns `rcutils_string_array_t` and `rmw_names_and_types_t`, which
81 * ALLOCATE — two levels deep for names-and-types. There is no allocator at this
82 * seam, and a caller-provides-the-buffer shape is worse than it looks: the ROS
83 * graph has no bound the CALLER can know, so a 128 KiB image would have to
84 * reserve permanently for the worst graph it might ever meet, and the backend
85 * would still have to materialise the whole list to fill the buffer.
86 *
87 * So enumeration is a VISITOR. Peak extra RAM is one entry, the backend streams
88 * from state it already holds, and a caller with a bound stops early by
89 * returning `false` — a normal outcome, not a truncation error. Same shape as
90 * `process_raw_in_place` and `publish_streamed` already use here.
91 *
92 * Every string handed to a visitor is BORROWED for that call only.
93 */

189 *
190 * These six returned `void`. That was never a target constraint: upstream
191 * returns `rmw_ret_t` from all of them, and a backend that cannot release a
192 * handle — a queue still draining, a token from another publisher, a
193 * double-destroy — had no way to say so. The runtime then reported success it

195 * shows up in a log and a leak that shows up as an allocation failure an hour

399 /* ---- Status events: how the three upstream parts map here ----
400 *
401 * Upstream's model is three-part: `*_event_init` fills an `rmw_event_t`
402 * HANDLE, `rmw_event_set_callback` attaches a callback to that handle, and
403 * `rmw_take_event` polls it for a status.
404 *
405 * - `rmw_event_set_callback` is FUSED into `*_event_init`, which takes the
406 * callback directly. There is no handle to attach one to afterwards.
407 * What that costs is real and small: upstream can replace or clear a
408 * callback later, and we cannot.
409 *
410 * - `rmw_take_event` is a SLOT (issue 0780), split per entity kind
411 * because we have no `rmw_event_t` to carry the entity — see
412 * `subscription_take_event` / `publisher_take_event` below.
413 *
414 * It was DECLINED until 2026-08-25 on two clauses that both turned out
415 * false, and they are worth recording because each sounded right:
416 *
417 * "Upstream polls because the WAIT SET said one was ready, and the wait
418 * set is declined here, so a poll would be blind."
419 * — This ABI is a poll-WITHOUT-a-wait-set design by construction.
420 * `has_data`'s own doc says so: "the poll a loop with no wait-set
421 * needs, and it allocates nothing." A poll with no wait set is the
422 * model here, not a blindness.
423 *
424 * "Our callback already runs on the safe context — from inside
425 * `drive_io`, on the executor thread, never an ISR or a transport
426 * thread."
427 * — True of no backend. zenoh fires from `try_recv_raw` and
428 * `has_data`; cyclonedds' DDS listeners fire on Cyclone's own
429 * worker thread while its `drive_io` is a sleep with no callback
430 * path at all. So a cyclonedds status event has nowhere safe to be
431 * delivered from, and buffer-plus-poll IS `take_event`. A
432 * per-backend fact stated ABI-wide — the same shape as the
433 * network-flow decline W5 flipped.
434 */

1171 /* ---- Phase 376 W4 — graph node lifecycle (optional) ----
1172 *
1173 * The rest of upstream's lifecycle group is deliberately absent, and the
1174 * absences are decisions rather than omissions:
1175 *
1176 * - `rmw_init` / `rmw_shutdown` / `rmw_context_fini` are
1177 * `create_session` / `destroy_session`. There is no second teardown
1178 * phase: the session shell is caller-owned, so there is nothing left to
1179 * free after the backend releases `backend_data`.
1180 *
1181 * - `rmw_init_options_{init,copy,fini}` have nothing to do here. Upstream
1182 * needs the trio because its options OWN heap and carry an
1183 * `rcutils_allocator_t`, which cannot cross this seam; ours is a
1184 * build-time POD, so "copy" is `=` and "fini" is nothing.
1185 *
1186 * This does NOT decide what the options CARRY. Of Humble's eight
1187 * fields, `create_session` takes `domain_id`; `implementation_identifier`
1188 * and `impl` are answered elsewhere (the identity slot,
1189 * `rmw_session_t::backend_data`); `allocator` is declined ABI-wide and
1190 * `instance_id` is rcl-side process identity. `security_options` is
1191 * declined on the target: it is a DDS-SROS2 keystore PATH plus an
1192 * enforcement switch, and neither a filesystem nor a security plugin
1193 * exists where this ABI runs. `localhost_only` and `enclave` are real
1194 * GAPS — issue 0785, to be carried by whatever shape issue 0808 gives
1195 * backend-private session config, because this flat argument list
1196 * cannot grow either without another ABI break.
1197 *
1198 * `discovery_options` is NOT in this list: it is an IRON field, and the
1199 * recorded contract is Humble. It was named here until issue 0785, the
1200 * third unchecked sentence about an upstream struct in this campaign
1201 * (issue 0777 supplied the other two). Read the header, not the memory.
1202 *
1203 * - `rmw_wait`, the wait set, and the guard conditions are declined
1204 * together, because `has_data` / `has_request` + `drive_io` +
1205 * `set_wake_callback` + `next_deadline_ms` ARE upstream's `rmw_wait`,
1206 * decomposed. What a vtable `wait` would add is only the BLOCK, moved
1207 * from the platform into the backend — and the block cannot live there:
1208 * one executor drives sessions from several backends at once
1209 * (`create_node_on(name, rmw)`), timers fire off the platform clock, and
1210 * guard conditions fire from another thread or an ISR. A backend can
1211 * only block on its own handles. `next_deadline_ms` is exactly the piece
1212 * of `rmw_wait` that CANNOT be answered above the seam, and it is
1213 * already a slot; that is the decomposition working, not a gap.
1214 */
