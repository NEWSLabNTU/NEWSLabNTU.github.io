4/* Phase 376 W3.a — this header defines the GENERIC RMW ABI: its types are
5 * `rmw_publisher_t`, `rmw_ret_t`, and so on, with no vendor prefix, because a
6 * backend author implements RMW rather than nano-ros.
7 *
8 * That makes it impossible to share a translation unit with upstream's
9 * `<rmw/rmw.h>`, which defines the same names differently. Refuse LOUDLY rather
10 * than let one definition silently win a redefinition race — two types of one
11 * name whose layouts disagree is the class this repo has already paid for three
12 * times in hand-mirrored FFI structs.
13 *
14 * A target image never links real rmw, and host-side consumers reach the
15 * backend through Rust, so nothing in this repo trips this today. It exists for
16 * the day something does. */

78/* ---- Phase 376 W4 — graph enumeration visitors ----
79 *
80 * Upstream returns `rcutils_string_array_t` and `rmw_names_and_types_t`, which
81 * ALLOCATE — two levels deep for names-and-types. There is no allocator at this
82 * seam, and a caller-provides-the-buffer shape is worse than it looks: the ROS
83 * graph has no bound the CALLER can know, so a 128 KiB image would have to
84 * reserve permanently for the worst graph it might ever meet, and the backend
85 * would still have to materialise the whole list to fill the buffer.
86 *
87 * So enumeration is a VISITOR. Peak extra RAM is one entry, the backend streams
88 * from state it already holds, and a caller with a bound stops early by
89 * returning `false` — a normal outcome, not a truncation error. Same shape as
90 * `process_raw_in_place` and `publish_streamed` already use here.
91 *
92 * Every string handed to a visitor is BORROWED for that call only.
93 */

111/* Phase 376 W5 — teardown and loan-return REPORT.
112 *
113 * These six returned `void`. That was never a target constraint: upstream
114 * returns `rmw_ret_t` from all of them, and a backend that cannot release a
115 * handle — a queue still draining, a token from another publisher, a
116 * double-destroy — had no way to say so. The runtime then reported success it
117 * had not verified, which on an RTOS is the difference between a leak that
118 * shows up in a log and a leak that shows up as an allocation failure an hour
119 * later with no provenance.
120 *
121 * A caller that genuinely has nothing to do with the status may ignore it;
122 * `void` denied it the choice. Backends that cannot fail return
123 * `NROS_RMW_RET_OK` unconditionally, which costs one instruction and keeps the
124 * signature honest for the ones that can.

286 /* ---- Phase 376 W4 — why there is no `take_event` and no
287 * `event_set_callback` ----
288 *
289 * Upstream's status-event model is three-part: `*_event_init` fills an
290 * `rmw_event_t` HANDLE, `rmw_event_set_callback` attaches a callback to that
291 * handle, and `rmw_take_event` polls it for a status the wait set said was
292 * ready. Ours fuses the first two and declines the third.
293 *
294 * - `rmw_event_set_callback` is FUSED: our `*_event_init` takes the
295 * callback, so there is no handle to attach one to afterwards. What that
296 * costs is real and small — upstream can replace or clear a callback
297 * later, and we cannot.
298 *
299 * - `rmw_take_event` is DECLINED, and the reason is not merely "no handle".
300 * Upstream polls an event because the WAIT SET told it one was ready, and
301 * the wait set is declined here (see the lifecycle block); without it a
302 * poll would be blind. More to the point, upstream's poll exists to move
303 * status handling OFF the notification context onto a safe one — and our
304 * callback already runs on the safe one: it is invoked from inside
305 * `drive_io`, on the executor thread, never from an ISR or a transport
306 * thread. The deferral upstream needs has already happened by the time
307 * the callback fires.
308 */

945 /* ---- Phase 376 W4 — graph node lifecycle (optional) ----
946 *
947 * The rest of upstream's lifecycle group is deliberately absent, and the
948 * absences are decisions rather than omissions:
949 *
950 * - `rmw_init` / `rmw_shutdown` / `rmw_context_fini` are
951 * `create_session` / `destroy_session`. There is no second teardown
952 * phase: the session shell is caller-owned, so there is nothing left to
953 * free after the backend releases `backend_data`.
954 *
955 * - `rmw_init_options_{init,copy,fini}` have nothing to do here. Upstream
956 * needs the trio because its options OWN heap and carry an
957 * `rcutils_allocator_t`, which cannot cross this seam; ours is a
958 * build-time POD, so "copy" is `=` and "fini" is nothing. (This does NOT
959 * decide `security_options` / `discovery_options`, which we answer
960 * nowhere — see the phase doc.)
961 *
962 * - `rmw_wait`, the wait set, and the guard conditions are declined
963 * together, because `has_data` / `has_request` + `drive_io` +
964 * `set_wake_callback` + `next_deadline_ms` ARE upstream's `rmw_wait`,
965 * decomposed. What a vtable `wait` would add is only the BLOCK, moved
966 * from the platform into the backend — and the block cannot live there:
967 * one executor drives sessions from several backends at once
968 * (`create_node_on(name, rmw)`), timers fire off the platform clock, and
969 * guard conditions fire from another thread or an ISR. A backend can
970 * only block on its own handles. `next_deadline_ms` is exactly the piece
971 * of `rmw_wait` that CANNOT be answered above the seam, and it is
972 * already a slot; that is the decomposition working, not a gap.
973 */
