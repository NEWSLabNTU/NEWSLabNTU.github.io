4/* Phase 376 W3.a — this header defines the GENERIC RMW ABI: its types are
5 * `rmw_publisher_t`, `rmw_ret_t`, and so on, with no vendor prefix, because a
6 * backend author implements RMW rather than nano-ros.
7 *
8 * That makes it impossible to share a translation unit with upstream's
9 * `<rmw/rmw.h>`, which defines the same names differently. Refuse LOUDLY rather
10 * than let one definition silently win a redefinition race — two types of one
11 * name whose layouts disagree is the class this repo has already paid for three
12 * times in hand-mirrored FFI structs.
13 *
14 * A target image never links real rmw, and host-side consumers reach the
15 * backend through Rust, so nothing in this repo trips this today. It exists for
16 * the day something does. */

63/* ---- Phase 376 W4 — graph enumeration visitors ----
64 *
65 * Upstream returns `rcutils_string_array_t` and `rmw_names_and_types_t`, which
66 * ALLOCATE — two levels deep for names-and-types. There is no allocator at this
67 * seam, and a caller-provides-the-buffer shape is worse than it looks: the ROS
68 * graph has no bound the CALLER can know, so a 128 KiB image would have to
69 * reserve permanently for the worst graph it might ever meet, and the backend
70 * would still have to materialise the whole list to fill the buffer.
71 *
72 * So enumeration is a VISITOR. Peak extra RAM is one entry, the backend streams
73 * from state it already holds, and a caller with a bound stops early by
74 * returning `false` — a normal outcome, not a truncation error. Same shape as
75 * `process_raw_in_place` and `publish_streamed` already use here.
76 *
77 * Every string handed to a visitor is BORROWED for that call only.
78 */

249 /* ---- Phase 376 W4 — why there is no `take_event` and no
250 * `event_set_callback` ----
251 *
252 * Upstream's status-event model is three-part: `*_event_init` fills an
253 * `rmw_event_t` HANDLE, `rmw_event_set_callback` attaches a callback to that
254 * handle, and `rmw_take_event` polls it for a status the wait set said was
255 * ready. Ours fuses the first two and declines the third.
256 *
257 * - `rmw_event_set_callback` is FUSED: our `*_event_init` takes the
258 * callback, so there is no handle to attach one to afterwards. What that
259 * costs is real and small — upstream can replace or clear a callback
260 * later, and we cannot.
261 *
262 * - `rmw_take_event` is DECLINED, and the reason is not merely "no handle".
263 * Upstream polls an event because the WAIT SET told it one was ready, and
264 * the wait set is declined here (see the lifecycle block); without it a
265 * poll would be blind. More to the point, upstream's poll exists to move
266 * status handling OFF the notification context onto a safe one — and our
267 * callback already runs on the safe one: it is invoked from inside
268 * `drive_io`, on the executor thread, never from an ISR or a transport
269 * thread. The deferral upstream needs has already happened by the time
270 * the callback fires.
271 */

853 /* ---- Phase 376 W4 — graph node lifecycle (optional) ----
854 *
855 * The rest of upstream's lifecycle group is deliberately absent, and the
856 * absences are decisions rather than omissions:
857 *
858 * - `rmw_init` / `rmw_shutdown` / `rmw_context_fini` are
859 * `create_session` / `destroy_session`. There is no second teardown
860 * phase: the session shell is caller-owned, so there is nothing left to
861 * free after the backend releases `backend_data`.
862 *
863 * - `rmw_init_options_{init,copy,fini}` have nothing to do here. Upstream
864 * needs the trio because its options OWN heap and carry an
865 * `rcutils_allocator_t`, which cannot cross this seam; ours is a
866 * build-time POD, so "copy" is `=` and "fini" is nothing. (This does NOT
867 * decide `security_options` / `discovery_options`, which we answer
868 * nowhere — see the phase doc.)
869 *
870 * - `rmw_wait`, the wait set, and the guard conditions are declined
871 * together, because `has_data` / `has_request` + `drive_io` +
872 * `set_wake_callback` + `next_deadline_ms` ARE upstream's `rmw_wait`,
873 * decomposed. What a vtable `wait` would add is only the BLOCK, moved
874 * from the platform into the backend — and the block cannot live there:
875 * one executor drives sessions from several backends at once
876 * (`create_node_on(name, rmw)`), timers fire off the platform clock, and
877 * guard conditions fire from another thread or an ISR. A backend can
878 * only block on its own handles. `next_deadline_ms` is exactly the piece
879 * of `rmw_wait` that CANNOT be answered above the seam, and it is
880 * already a slot; that is the decomposition working, not a gap.
881 */
