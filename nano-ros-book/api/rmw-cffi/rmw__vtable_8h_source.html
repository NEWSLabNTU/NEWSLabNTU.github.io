4/* Phase 376 W3.a — this header defines the GENERIC RMW ABI: its types are
5 * `rmw_publisher_t`, `rmw_ret_t`, and so on, with no vendor prefix, because a
6 * backend author implements RMW rather than nano-ros.
7 *
8 * That makes it impossible to share a translation unit with upstream's
9 * `<rmw/rmw.h>`, which defines the same names differently. Refuse LOUDLY rather
10 * than let one definition silently win a redefinition race — two types of one
11 * name whose layouts disagree is the class this repo has already paid for three
12 * times in hand-mirrored FFI structs.

15 * backend through Rust, so nothing in this repo trips this today. It exists for
16 * the day something does. */

81/* ---- Phase 376 W4 — graph enumeration visitors ----
82 *
83 * Upstream returns `rcutils_string_array_t` and `rmw_names_and_types_t`, which
84 * ALLOCATE — two levels deep for names-and-types. There is no allocator at this
85 * seam, and a caller-provides-the-buffer shape is worse than it looks: the ROS
86 * graph has no bound the CALLER can know, so a 128 KiB image would have to
87 * reserve permanently for the worst graph it might ever meet, and the backend
88 * would still have to materialise the whole list to fill the buffer.
89 *
90 * So enumeration is a VISITOR. Peak extra RAM is one entry, the backend streams
91 * from state it already holds, and a caller with a bound stops early by
92 * returning `false` — a normal outcome, not a truncation error. Same shape as
93 * `process_raw_in_place` and `publish_streamed` already use here.
94 *
95 * Every string handed to a visitor is BORROWED for that call only.
96 */

180 *
181 * These six returned `void`. That was never a target constraint: upstream
182 * returns `rmw_ret_t` from all of them, and a backend that cannot release a
183 * handle — a queue still draining, a token from another publisher, a

407 /* ---- Status events: how the three upstream parts map here ----
408 *
409 * Upstream's model is three-part: `*_event_init` fills an `rmw_event_t`
410 * HANDLE, `rmw_event_set_callback` attaches a callback to that handle, and
411 * `rmw_take_event` polls it for a status.
412 *
413 * - `rmw_event_set_callback` is FUSED into `*_event_init`, which takes the
414 * callback directly. There is no handle to attach one to afterwards.
415 * What that costs is real and small: upstream can replace or clear a
416 * callback later, and we cannot.
417 *
418 * - `rmw_take_event` is a SLOT (issue 0780), split per entity kind
419 * because we have no `rmw_event_t` to carry the entity — see
420 * `subscription_take_event` / `publisher_take_event` below.
421 *
422 * It was DECLINED until 2026-08-25 on two clauses that both turned out
423 * false, and they are worth recording because each sounded right:
424 *
425 * "Upstream polls because the WAIT SET said one was ready, and the wait
426 * set is declined here, so a poll would be blind."
427 * — This ABI is a poll-WITHOUT-a-wait-set design by construction.
428 * `has_data`'s own doc says so: "the poll a loop with no wait-set
429 * needs, and it allocates nothing." A poll with no wait set is the
430 * model here, not a blindness.
431 *
432 * "Our callback already runs on the safe context — from inside
433 * `drive_io`, on the executor thread, never an ISR or a transport
434 * thread."
435 * — True of no backend. zenoh fires from `take` and
436 * `has_data`; cyclonedds' DDS listeners fire on Cyclone's own
437 * worker thread while its `drive_io` is a sleep with no callback
438 * path at all. So a cyclonedds status event has nowhere safe to be
439 * delivered from, and buffer-plus-poll IS `take_event`. A
440 * per-backend fact stated ABI-wide — the same shape as the
441 * network-flow decline W5 flipped.
442 */

1165 /* ---- Phase 376 W4 — graph node lifecycle (optional) ----
1166 *
1167 * The rest of upstream's lifecycle group is deliberately absent, and the
1168 * absences are decisions rather than omissions:
1169 *
1170 * - `rmw_init` / `rmw_shutdown` / `rmw_context_fini` are
1171 * `create_session` / `destroy_session`. There is no second teardown
1172 * phase: the session shell is caller-owned, so there is nothing left to
1173 * free after the backend releases `backend_data`.
1174 *
1175 * - `rmw_init_options_{init,copy,fini}` have nothing to do here. Upstream
1176 * needs the trio because its options OWN heap and carry an
1177 * `rcutils_allocator_t`, which cannot cross this seam; ours is a
1178 * build-time POD, so "copy" is `=` and "fini" is nothing.
1179 *
1180 * This does NOT decide what the options CARRY. Of Humble's eight
1181 * fields, `create_session` takes `domain_id`; `implementation_identifier`
1182 * and `impl` are answered elsewhere (the identity slot,
1183 * `rmw_session_t::backend_data`); `allocator` is declined ABI-wide and
1184 * `instance_id` is rcl-side process identity. `security_options` is
1185 * declined on the target: it is a DDS-SROS2 keystore PATH plus an
1186 * enforcement switch, and neither a filesystem nor a security plugin
1187 * exists where this ABI runs. `localhost_only` and `enclave` are real
1188 * GAPS — issue 0785, to be carried by whatever shape issue 0808 gives
1189 * backend-private session config, because this flat argument list
1190 * cannot grow either without another ABI break.
1191 *
1192 * `discovery_options` is NOT in this list: it is an IRON field, and the
1193 * recorded contract is Humble. It was named here until issue 0785, the
1194 * third unchecked sentence about an upstream struct in this campaign
1195 * (issue 0777 supplied the other two). Read the header, not the memory.
1196 *
1197 * - `rmw_wait`, the wait set, and the guard conditions are declined
1198 * together, because `has_data` / `has_request` + `drive_io` +
1199 * `set_wake_callback` + `next_deadline_ms` ARE upstream's `rmw_wait`,
1200 * decomposed. What a vtable `wait` would add is only the BLOCK, moved
1201 * from the platform into the backend — and the block cannot live there:
1202 * one executor drives sessions from several backends at once
1203 * (`create_node_on(name, rmw)`), timers fire off the platform clock, and
1204 * guard conditions fire from another thread or an ISR. A backend can
1205 * only block on its own handles. `next_deadline_ms` is exactly the piece
1206 * of `rmw_wait` that CANNOT be answered above the seam, and it is
1207 * already a slot; that is the decomposition working, not a gap.
1208 */
