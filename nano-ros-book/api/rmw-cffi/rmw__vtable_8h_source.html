4/* Phase 376 W3.a — this header defines the GENERIC RMW ABI: its types are
5 * `rmw_publisher_t`, `rmw_ret_t`, and so on, with no vendor prefix, because a
6 * backend author implements RMW rather than nano-ros.
7 *
8 * That makes it impossible to share a translation unit with upstream's
9 * `<rmw/rmw.h>`, which defines the same names differently. Refuse LOUDLY rather
10 * than let one definition silently win a redefinition race — two types of one
11 * name whose layouts disagree is the class this repo has already paid for three
12 * times in hand-mirrored FFI structs.
13 *
14 * A target image never links real rmw, and host-side consumers reach the
15 * backend through Rust, so nothing in this repo trips this today. It exists for
16 * the day something does. */

78/* ---- Phase 376 W4 — graph enumeration visitors ----
79 *
80 * Upstream returns `rcutils_string_array_t` and `rmw_names_and_types_t`, which
81 * ALLOCATE — two levels deep for names-and-types. There is no allocator at this
82 * seam, and a caller-provides-the-buffer shape is worse than it looks: the ROS
83 * graph has no bound the CALLER can know, so a 128 KiB image would have to
84 * reserve permanently for the worst graph it might ever meet, and the backend
85 * would still have to materialise the whole list to fill the buffer.
86 *
87 * So enumeration is a VISITOR. Peak extra RAM is one entry, the backend streams
88 * from state it already holds, and a caller with a bound stops early by
89 * returning `false` — a normal outcome, not a truncation error. Same shape as
90 * `process_raw_in_place` and `publish_streamed` already use here.
91 *
92 * Every string handed to a visitor is BORROWED for that call only.
93 */

111/* Phase 376 W5 — teardown and loan-return REPORT.
112 *
113 * These six returned `void`. That was never a target constraint: upstream
114 * returns `rmw_ret_t` from all of them, and a backend that cannot release a
115 * handle — a queue still draining, a token from another publisher, a
116 * double-destroy — had no way to say so. The runtime then reported success it
117 * had not verified, which on an RTOS is the difference between a leak that
118 * shows up in a log and a leak that shows up as an allocation failure an hour
119 * later with no provenance.
120 *
121 * A caller that genuinely has nothing to do with the status may ignore it;
122 * `void` denied it the choice. Backends that cannot fail return
123 * `NROS_RMW_RET_OK` unconditionally, which costs one instruction and keeps the
124 * signature honest for the ones that can.

313 /* ---- Status events: how the three upstream parts map here ----
314 *
315 * Upstream's model is three-part: `*_event_init` fills an `rmw_event_t`
316 * HANDLE, `rmw_event_set_callback` attaches a callback to that handle, and
317 * `rmw_take_event` polls it for a status.
318 *
319 * - `rmw_event_set_callback` is FUSED into `*_event_init`, which takes the
320 * callback directly. There is no handle to attach one to afterwards.
321 * What that costs is real and small: upstream can replace or clear a
322 * callback later, and we cannot.
323 *
324 * - `rmw_take_event` is a SLOT (issue 0780), split per entity kind
325 * because we have no `rmw_event_t` to carry the entity — see
326 * `subscription_take_event` / `publisher_take_event` below.
327 *
328 * It was DECLINED until 2026-08-25 on two clauses that both turned out
329 * false, and they are worth recording because each sounded right:
330 *
331 * "Upstream polls because the WAIT SET said one was ready, and the wait
332 * set is declined here, so a poll would be blind."
333 * — This ABI is a poll-WITHOUT-a-wait-set design by construction.
334 * `has_data`'s own doc says so: "the poll a loop with no wait-set
335 * needs, and it allocates nothing." A poll with no wait set is the
336 * model here, not a blindness.
337 *
338 * "Our callback already runs on the safe context — from inside
339 * `drive_io`, on the executor thread, never an ISR or a transport
340 * thread."
341 * — True of no backend. zenoh fires from `try_recv_raw` and
342 * `has_data`; cyclonedds' DDS listeners fire on Cyclone's own
343 * worker thread while its `drive_io` is a sleep with no callback
344 * path at all. So a cyclonedds status event has nowhere safe to be
345 * delivered from, and buffer-plus-poll IS `take_event`. A
346 * per-backend fact stated ABI-wide — the same shape as the
347 * network-flow decline W5 flipped.
348 */

1070 /* ---- Phase 376 W4 — graph node lifecycle (optional) ----
1071 *
1072 * The rest of upstream's lifecycle group is deliberately absent, and the
1073 * absences are decisions rather than omissions:
1074 *
1075 * - `rmw_init` / `rmw_shutdown` / `rmw_context_fini` are
1076 * `create_session` / `destroy_session`. There is no second teardown
1077 * phase: the session shell is caller-owned, so there is nothing left to
1078 * free after the backend releases `backend_data`.
1079 *
1080 * - `rmw_init_options_{init,copy,fini}` have nothing to do here. Upstream
1081 * needs the trio because its options OWN heap and carry an
1082 * `rcutils_allocator_t`, which cannot cross this seam; ours is a
1083 * build-time POD, so "copy" is `=` and "fini" is nothing.
1084 *
1085 * This does NOT decide what the options CARRY. Of Humble's eight
1086 * fields, `create_session` takes `domain_id`; `implementation_identifier`
1087 * and `impl` are answered elsewhere (the identity slot,
1088 * `rmw_session_t::backend_data`); `allocator` is declined ABI-wide and
1089 * `instance_id` is rcl-side process identity. `security_options` is
1090 * declined on the target: it is a DDS-SROS2 keystore PATH plus an
1091 * enforcement switch, and neither a filesystem nor a security plugin
1092 * exists where this ABI runs. `localhost_only` and `enclave` are real
1093 * GAPS — issue 0785, to be carried by whatever shape issue 0808 gives
1094 * backend-private session config, because this flat argument list
1095 * cannot grow either without another ABI break.
1096 *
1097 * `discovery_options` is NOT in this list: it is an IRON field, and the
1098 * recorded contract is Humble. It was named here until issue 0785, the
1099 * third unchecked sentence about an upstream struct in this campaign
1100 * (issue 0777 supplied the other two). Read the header, not the memory.
1101 *
1102 * - `rmw_wait`, the wait set, and the guard conditions are declined
1103 * together, because `has_data` / `has_request` + `drive_io` +
1104 * `set_wake_callback` + `next_deadline_ms` ARE upstream's `rmw_wait`,
1105 * decomposed. What a vtable `wait` would add is only the BLOCK, moved
1106 * from the platform into the backend — and the block cannot live there:
1107 * one executor drives sessions from several backends at once
1108 * (`create_node_on(name, rmw)`), timers fire off the platform clock, and
1109 * guard conditions fire from another thread or an ISR. A backend can
1110 * only block on its own handles. `next_deadline_ms` is exactly the piece
1111 * of `rmw_wait` that CANNOT be answered above the seam, and it is
1112 * already a slot; that is the decomposition working, not a gap.
1113 */
