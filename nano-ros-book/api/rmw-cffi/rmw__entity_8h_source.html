43/* Policy values carry UPSTREAM's numbering.
44 *
45 * They did not until 2026-08-24, and the disagreement was not academic. Ours
46 * were a dense 0/1 pair per policy, which put a DIFFERENT meaning on the same
47 * integer:
48 *
49 * value | upstream | ours (before)
50 * ------|-----------------------------------|-------------------
51 * 0 | *_SYSTEM_DEFAULT | BEST_EFFORT / VOLATILE / KEEP_LAST
52 * 1 | RELIABLE / TRANSIENT_LOCAL / KEEP_LAST | RELIABLE / TRANSIENT_LOCAL / KEEP_ALL
53 *
54 * so `HISTORY == 1` meant KEEP_LAST to upstream and KEEP_ALL to us — the two
55 * opposite answers to the question. Liveliness was worse: MANUAL_BY_NODE and
56 * MANUAL_BY_TOPIC were SWAPPED (2 and 3).
57 *
58 * These values cross the ABI. `rmw_qos_profile_check_compatible` is a name
59 * upstream owns and we export, and the cyclonedds backend translates this
60 * struct into real DDS QoS that a ROS peer matches against. A caller reasoning
61 * in upstream's vocabulary got silently wrong policies. Same argument as W3.d
62 * step B for the return codes: where a value crosses the boundary, upstream's
63 * numbering is the only one that cannot be wrong.
64 *
65 * The names keep the `NROS_RMW_` prefix — as the return codes do — because the
66 * set is ours to extend, not upstream's to define.
67 */

466/* ====================================================================
467 * The two PURE functions.
468 *
469 * Plain exported C functions, deliberately NOT vtable slots, and the reason is
470 * the campaign's own rule read the other way round: a vtable slot is the
471 * mechanism for letting backends DIFFER, and these two must not. Both compute
472 * over types this header defines; if two backends disagreed about whether a QoS
473 * pair is compatible, or whether two gids name the same entity, that is a
474 * DEFECT with as many places to fix it as there are backends.
475 *
476 * Three supporting reasons:
477 *
478 * - The useful call sites have no vtable to dispatch through. QoS
479 * compatibility is wanted at `create_*` time (that is what produces
480 * `NROS_RMW_RET_INCOMPATIBLE_QOS`), in codegen'd validation, and in host
481 * tooling with no session. Neither function takes an entity, so a slot would
482 * force a caller to invent a session — and neither could be called BEFORE a
483 * backend registers, which is exactly when create-time validation runs.
484 *
485 * - Upstream is not evidence for a slot. `rmw_qos_profile_check_compatible`
486 * lives in `rmw/qos_profiles.h` and is defined by librmw ITSELF; it appears
487 * in the implementation contract only because each `librmw_*_cpp.so`
488 * statically links librmw and re-exports it. That is plugin packaging, not
489 * semantics, and we load no plugin.
490 *
491 * - Precedent: `nros_rmw_cffi_register_named` and friends are declared here
492 * and defined once in Rust with `#[no_mangle]`, so `nros-rmw-abi` stays a
493 * header-only INTERFACE target — no new compiled TU, no new link edge.
494 * (`static inline` was the alternative and is worse: bindgen does not emit
495 * it, so the C-headers-as-SSoT rule would force a SECOND Rust implementation, which is the
496 * first reason again.)
497 * ==================================================================== */

861/* ---- Standard QoS profile constants ---- */
862/*
863 * Compound-literal macros rather than `static const` objects, so a profile is
864 * usable in every TU that includes this header with no storage and no
865 * initialisation order.
866 *
867 * **ONE STATEMENT PER PROFILE.** Every profile below is a
868 * single line through `NROS_RMW_QOS_PROFILE_FROM_POLICIES`, which is the ONLY
869 * place the fields that never vary between profiles — `_reserved0`, the three
870 * durations, `avoid_ros_namespace_conventions`, `_reserved1` — are written.
871 * They used to be written out per profile: 26 constants in one file held in
872 * agreement by eye, and the four profiles carrying a concrete liveliness had
873 * all drifted the same way while their doc comments asserted the drifted value
874 * was upstream's.
875 *
876 * **The values are UPSTREAM's, and this file is a TRANSCRIPTION of them.** An
877 * embedded image cannot include `rmw/qos_profiles.h` and an offline build has
878 * no ROS install to read, so the numbers have to live here. That makes them
879 * exactly the kind of copy that drifts, so they are not maintained by hand
880 * alone: `scripts/check-qos-profile-ssot.py` binds every profile below to the
881 * Rust SSoT (`nros_rmw::QoSProfile`'s `QOS_PROFILE_*` constants) and, when a
882 * ROS install is resolvable, re-derives both against
883 * `<prefix>/include/rmw/rmw/qos_profiles.h`. Edit a value here without the
884 * gate agreeing and the gate is what tells you.
885 *
886 * That named `scripts/check-qos-profile-table.py` from 2026-09-05 until a later
887 * fix, and NO SUCH SCRIPT EXISTED for any of it. Two gates were written for the profile table
888 * and the duplicate was deleted — correctly, one parser of one table — but this
889 * prose kept the deleted name, so the transcription claiming loudest to be
890 * checked was the one checked by nothing. W1 wrote the coverage the sentence
891 * had been describing, into the gate that survived.
892 */

919/* LIVELINESS IS THE SENTINEL IN EVERY CONCRETE PROFILE.
920 *
921 * `DEFAULT`, `SENSOR_DATA`, `SERVICES_DEFAULT` and `PARAMETERS` carried
922 * `NROS_RMW_LIVELINESS_AUTOMATIC` (1) until 2026-09-05, under doc comments
923 * reading "`rmw_qos_profile_default`-equivalent … automatic liveliness".
924 * Upstream's own initialisers say `RMW_QOS_POLICY_LIVELINESS_SYSTEM_DEFAULT`
925 * for all seven profiles, `rmw_qos_profile_unknown` excepted — there is no
926 * upstream profile that asks for AUTOMATIC. This is the F2 class: 0829 fixed
927 * `SYSTEM_DEFAULT`'s liveliness because that was the profile being looked at,
928 * and the four siblings carrying the same wrong value were not swept.
929 *
930 * THIS CHANGES WHAT A BACKEND COMPILES AGAINST, so what it does to the wire is
931 * stated rather than assumed. The two in-tree consumers of a changed macro are
932 * `nros-rmw-cyclonedds`'s `create_service` / `create_client`
933 * (`NROS_RMW_QOS_PROFILE_SERVICES_DEFAULT` when the caller passes NULL) and
934 * `nros-rmw-xrce`'s (same); the cyclone unit tests use `_DEFAULT`.
935 * - cyclonedds: `make_dds_qos` calls `dds_qset_liveliness` only when the kind
936 * is NOT the sentinel (`qos.cpp:99`), so AUTOMATIC(1) set
937 * `DDS_LIVELINESS_AUTOMATIC` + `DDS_INFINITY` explicitly and the sentinel
938 * omits the call — leaving Cyclone's own default, which the DDS spec fixes
939 * at AUTOMATIC with an infinite lease. Same offered QoS on the wire.
940 * - xrce: drops liveliness entirely (it lowers no liveliness field), so the
941 * value is unobservable there either way.
942 * - zenoh: reads no QoS field at all.
943 * A backend that starts honouring liveliness later sees the correct
944 * "middleware's choice" here rather than an unrequested AUTOMATIC.
945 */
