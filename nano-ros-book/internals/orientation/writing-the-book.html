nano-ros Internals

Writing the Book

This page is for anyone who writes or reorganizes a page of the nano-ros Book, the user book under book/src/. It is the charter of RFC-0124 put as a checklist, followed by one template for each kind of page. Read the checklist before you open a template, and check your page against it before you ask for review.

check-book-audience reads the gated rules and refuses every departure from them, except the findings its baseline still lists (see The charter baseline). --charter lists each finding with its baseline key:

python3 scripts/check-book-audience.py --charter

The checklist

Who and why

  1. Three purposes, stated budgets. Every page serves at least one of education, field solutions and industrial, within its budget: a 15-minute install and labs under two hours; 30 minutes from box to ros2 topic echo; reproducible, auditable, offline builds (RFC-0116 D1).
  2. Two books by reader. Application developers and porters read the Book. Contributors read this book, Internals. Contributor material in a user page moves here.

What may be in the Book

  1. A board enters the Book only with an emulator twin, or a track that replays its chapter (RFC-0115 D4). QEMU mps2-an385 is the concepts board. Gated: a board page whose registry rows are neither Verified nor an emulator twin of a named board is refused.
  2. Claims follow the registry. Board facts and status words are generated, never typed. A board, feature or integration with no registry row gets no user page. Gated (rule E refuses a typed status word).
  3. Only the user tier. No nros dev, no checkout steps, no internal ids in prose. RFC numbers appear only in a closing “Design background”. Gated (rules D and check-user-surface-ids refuse).

How it is organized

  1. Sections follow what the reader is doing: Start here, Get started on your board, Tutorial, User guide, Background, Reference, Extending, Releases. RFC-0124 Appendix A names every page and its sources. A page not in Appendix A needs an RFC amendment first.
  2. One topic, one page per type. Tutorial, how-to, explanation and reference are separate pages that link to each other. A topic has at most one page of each type. Gated: the declared type must fit the section, and two pages may not declare the same type and topic.
  3. Starters before depth. Every admitted board has a starter that needs only Install, twin-and-hardware boards first.
  4. Reference is generated from its owner: the contract format, the CLI, the APIs, system.toml, boards. A hand-written table that copies a generated one is deleted.

How it is written

  1. Procedure first. A task page is steps. Each step is a command or an edit, followed by its expected output. The page ends with a complete working example.

  2. Concepts at the point of need. Explain a concept only if it is uncommon outside nano-ros and central inside it: the bringup, the image, the contract, static pools, the execution sched tasks. Start from the example in front of the reader, not from the model. For what a ROS 2 user knows, link to the ROS 2 documentation.

  3. The simplest working path first. Serial before ethernet, with WiFi stated as deferred. The first chapter names no launch file, image or entry. One run verb, nros run, with nros flash --monitor on hardware.

  4. Say plainly where nano-ros differs from ROS 2. Never imply a symmetry that is not there.

  5. Every runnable step is probed on its row’s evidence. A step that cannot run yet carries an awaits line on its track and fails loudly. Nothing is skipped. Gated: a shell fence (bash, sh, shell, zsh or fish) with no probe= is refused. A fence that is not a step, such as output, a file’s contents or a command with a placeholder the reader fills in, is tagged with what it is (text, console, toml), not bash.

  6. Budgets. Gated:

    TypeWords of prose
    how-to300–1,500
    tutorial chapter1,500–3,000
    explanation800–2,500
    referenceno limit, but tables and lookups only

    A page under 300 words is merged into its parent. Rust, C and C++ variants of one step are tabs on one page, not parallel pages.

Voice

Follow the Google developer documentation style guide: second person, present tense, active voice, sentence-case headings, and no “simply”, “just” or “easy”. Name a thing once, then use that name throughout.

The charter baseline

The gate refuses every finding of the rules above, except the ones .config/book-charter-baseline.txt lists: the findings that were left in the book when the rules began to refuse, in pages that other open work owns or that no track replays yet. Each row names one finding by the key --charter prints in its first column, then its reason or owner:

guide/rmw/use-cyclone-dds.md unprobed-steps=7  # probe coverage follow-up

The baseline only shrinks:

  • A finding it does not list is refused. Fix it; do not add a row.
  • A row that no longer fires is refused until you remove it.
  • A counted row (unprobed-steps=N) is refused when the page gains a step with no probe fence, and when it loses one, until you lower N to the new count.

To remove a row, fix its finding, then delete or lower the row in the same commit:

  1. Find the steps: python3 scripts/check-book-audience.py --charter prints each finding’s lines.

  2. Fix each one. Give a runnable step a probe= on a track that replays the page (a [[probe]] row in packages/boards/board-support.toml, then python3 scripts/gen-board-support.py and a recipe in just/probe.just). A step that cannot run yet still gets its probe=, on a track whose awaits names why. Tag a fence that is not a step with what it is. Merge a page under the floor into its parent through book/page-map.toml and scripts/book-move.py, so it keeps a redirect.

  3. Check that each track you touched still extracts:

    PROBE_EXTRACT_ONLY="$PWD/track.sh" PROBE_TRACK=installed PROBE_PLATFORM=<track> \
    bash scripts/probe/run-bootstrap-probe.sh && bash -n track.sh
python3 scripts/check-book-probe-tracks.py

  4. Run python3 scripts/check-book-audience.py. It names the row to delete or the count to lower.

Declare the type and level

Every hand-written user page carries one declaration on the line after its title. Generated pages are reference pages and carry none.

# Configure zenoh

<!-- type: how-to · level: 2 -->

The rendered book shows the declaration as a badge under the title, such as “How-to · Level 2: Building real applications”, so a reader sees the page’s kind and what it assumes. scripts/mdbook-level-badge.py renders it, with the level names of the table below.

Add · topic: <slug> when a topic has pages of several types, so the gate can tell that each type appears once:

<!-- type: tutorial · level: 2 · topic: contract -->

Topic levels

A page may assume only topics at its own level or below. It lists them on a “needs first” line, and the gate refuses a link to a higher level.

LevelTopicsWhere
1. First contactinstall; a board starter; run a talker; what you built; add a node; pick and configure the RMWStart, starters, Tutorial 1–4
2. Building real applicationsyour own message; services and actions; parameters and launch files; the contract and sizing; another target; ROS 2 interop and QoS; a serial link; logging; workspace layout; mixing languagesTutorial 5–10, User guide
3. Production and tuningconfiguring an image; build profiles; offline and vendored builds; deploying; static memory; scheduling and timing; throughput; bridges; porting a ROS 2 nodeUser guide, Background
4. Extending nano-rosa board, platform or transport; a custom RMW backend; runner and command packages; API designExtending, then Internals

A reference page carries the level of the most advanced topic it describes. Anyone may look it up.

Languages in tabs

When a step has a Rust, a C and a C++ version, write the versions as one tab group. The rendered book shows them as tabs, and the language a reader picks switches every group on the page and stays picked on the next page.

<!-- tabs -->

#### Rust

```rust
executor.spin_once(10)?;
```

#### C

```c
rclc_executor_spin_some(&executor, 10);
```

#### C++

```cpp
executor.spin_some(10);
```

<!-- /tabs -->

It renders as:

#![allow(unused)]
fn main() {
executor.spin_once(10)?;
}
rclc_executor_spin_some(&executor, 10);

executor.spin_some(10);

The rules:

  • <!-- tabs --> and <!-- /tabs --> each stand alone on a line, at column 0, so a group cannot sit inside a list or a quote.
  • The first line after <!-- tabs --> (blank lines aside) is a heading whose text is Rust, C or C++. Every heading at that level inside the group starts the next tab. Use one level below the section you are in.
  • A tab holds any markdown: prose, several fences, a list. Deeper headings are content. A group has at least two tabs and each language once.
  • Show only the languages the step has. Rust first, then C, then C++.

On GitHub, which does not run the preprocessor, a group reads as one sub-heading per language. The tab headings do not appear in the rendered page, so do not link to them.

A probe step inside a tab belongs to that tab’s language. Give each language’s version of a step the same probe=NN, and set lang (rust, c or cpp) on the [[probe]] row of each track that replays the page, in packages/boards/board-support.toml. The extractor keeps that language’s blocks and every untabbed one, and it refuses a tabbed step on a track that names no language. The charter counts a group’s prose once, as its longest tab.

scripts/mdbook-lang-tabs.py renders the groups and scripts/lib/book_tabs.py parses them. check-book-audience refuses a malformed group.

Before you ask for review

State in the PR description, for every page you add or rewrite:

  • its type, level and section in RFC-0124 Appendix A;
  • the principles you checked it against, and any you could not meet yet, with the reason (for example, a step waiting on a CLI change, with its awaits line);
  • the output of python3 scripts/check-book-audience.py --charter for that page.

Moves go through book/page-map.toml and scripts/book-move.py, so every moved page keeps a redirect. Land the work in section-sized PRs, rebased onto main rather than merging main in.
