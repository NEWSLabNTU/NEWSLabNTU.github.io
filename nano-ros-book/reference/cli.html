nros

nros — command-line tool for nano-ros (a lightweight ROS 2 client for embedded RTOS).

Quick start:
  nros setup <board>   provision a board's toolchains + sources (board-scoped)
  nros new <name>      scaffold a project
  nros configure       generate msg bindings, models and build settings
  nros plan            resolve a launch topology
  nros check           check a package, a plan or a workspace
  nros doctor          check SDK paths / toolchains / env

Run `nros setup --list` to see available packages, and `nros help --all` for the build-system tier as well.

Usage: nros [OPTIONS] [COMMAND]

Start:
  new          Scaffold a new nano-ros package (`--template`: talker, listener, server, client, action-server, action-client), workspace, image or component
  setup        Resolve + fetch a board's toolchain/SDK packages

Build:
  build        Build a nano-ros workspace
  configure    Configure a project: generate message bindings and the cargo patch config, then resolve and generate every image's build inputs
  clean        Remove the generated bindings and the managed patch block from each Rust package. Leaves user-written sections alone
  materialize  Take ownership of a generated entry package

Run on a target:
  run          Run an image on its target: a host process or an emulator. Builds it if stale, starts the router it needs, streams its console and stops everything on exit. `--expect` grades the console; `--dry-run [--why]` prints the resolved plan instead. A hardware image is `nros flash --monitor`
  flash        Flash an image onto a real board: builds it if stale, runs the board's human steps, flashes, and with `--monitor` watches the console on the same port. `--expect` grades it; `--dry-run [--why]` prints the plan instead
  monitor      Attach to a running board's console: `--expect` grades it, `--send` writes to it. In a workspace the image's board states the port and baud; elsewhere `--port` names the device
  bench        This machine's boards: `scan` records which attached USB device is which board in `$NROS_HOME/bench.toml`, `list` prints it with what is attached now. It supplies ports and probes, never test scope
  debug        Debug an image on its target (reserved: not available yet)

Workspace:
  list         List the workspace's packages: kind, name and directory per row
  graph        Print the workspace's packages in dependency order, each with the workspace packages it depends on

Interfaces:
  interface    Generate message bindings, list the interfaces the workspace can reach, or show one interface's definition

Inspect:
  doctor       Health-check the workspace (SDK paths, toolchains, env)
  board        Inspect supported boards
  config       Inspect or validate the current project's resolved configuration
  plan         Resolve launch files, manifests, and metadata into nros-plan.json
  check        Check a runner, command or board package, a plan, a system.toml or a workspace
  explain      Render a generated nros-plan.json in human-readable form

Toolchain:
  toolchain    List, remove and garbage-collect installed toolchains and SDK packages
  pin          Report this project's `nros-toolchain.toml`, or move it
  update       Move one pin, editing the pin set and leaving one diff
  locate       Print where a resource is, and with `--why`, which rung answered

Other:
  version      Print toolchain + library versions
  completions  Generate shell completions (bash | zsh | fish | powershell)
  help         Print this message or the help of the given subcommand(s)

Options:
      --codegen-version
          Print the codegen version this binary emits, and exit.
          
          The compatibility token between this binary's emitted code and the nano-ros runtime that compiles it — deliberately not a release version. A codegen-version refusal asks you to compare this number against the runtime's accepted range.

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version

Start

nros new

Scaffold a new nano-ros package (`--template`: talker, listener, server, client, action-server, action-client), workspace, image or component

Usage: nros new [OPTIONS] [NAME] [SYSTEM_NAME]

Arguments:
  [NAME]
          Project directory to create, or a mode keyword.
          
          The literal keyword `system` enters bringup-scaffold mode: `nros new system <name>_bringup --components <pkg1,pkg2,...>`.

  [SYSTEM_NAME]
          The bringup package directory, or the package name in a package-scaffold mode.
          
          The bringup directory when the first positional is the literal `system`; the <name> when it is the literal `platform` or `board`.

Options:
      --for-platform <FOR_PLATFORM>
          The platform a `nros new board <name>` targets.
          
          A platform directory name, e.g. `zephyr`, `bare-metal`, or one scaffolded via `nros new platform`.

      --components <COMPONENTS>
          Comma-separated component package names for `nros new system <bringup> --components <list>`

      --component-name <COMPONENT_NAME>
          One component package name; repeatable.
          
          An alternative to `--components <a,b,c>` when commas in the shell are awkward. Merged with `--components`.

      --workspace-root <WORKSPACE_ROOT>
          Workspace root holding the cargo `Cargo.toml` to update.
          
          Defaults to the parent of the bringup dir.

      --into <INTO>
          Parent dir under which the bringup package is created.
          
          Defaults to the current working directory.

      --no-config
          Skip the optional `config/` sub-dir

      --no-readme
          Skip the optional `README.md`

      --platform <PLATFORM>
          Target platform. In project mode give this or `--board`.
          
          `--board` alone reads the platform from the board. `linux` is the host board. `esp32` is not offered: ESP32 support is dormant.
          
          [possible values: linux, freertos, nuttx, threadx, zephyr, baremetal]

      --rmw <RMW>
          RMW backend. Defaults per mode: `zenoh` for project/component scaffolds (matches the tracked examples), `cyclonedds` for `--workspace` (needs no router — the quick-start default)
          
          [possible values: zenoh, xrce, cyclonedds]

      --ros-edition <ROS_EDITION>
          ROS edition (drives the `ros-<edition>` cargo feature). Defaults to the sourced ROS 2 (`$ROS_DISTRO`) when it is one of these, else humble
          
          [possible values: humble, iron, jazzy]

      --lang <LANG>
          Source language. Defaults per mode: `rust` for project/component scaffolds, `cpp` for `--workspace` (the quick-start language)
          
          [possible values: rust, c, cpp]

      --template <TEMPLATE>
          The node the package holds: a talker (std_msgs/String on /chatter), a listener, an AddTwoInts `server` / `client`, or a Fibonacci `action-server` / `action-client` — the roles of the ROS demos, under the demos' own interfaces. Default: `talker`
          
          [possible values: talker, listener, server, client, action-server, action-client]

      --node-name <NODE_NAME>
          The node's ROS name (as `ros2 pkg create --node-name`). Default: the package name (`-` spelled `_`); for `--component`, the role's demo node name (`talker`, `add_two_ints_server`, …)

      --dependencies <DEPENDENCIES>...
          Extra `<depend>` packages for package.xml, after the template's own interface package (as `ros2 pkg create --dependencies`). Space- or comma-separated

      --license <LICENSE>
          package.xml `<license>` (as `ros2 pkg create --license`). Default: `Apache-2.0`

      --description <DESCRIPTION>
          package.xml `<description>` (as `ros2 pkg create --description`)

      --maintainer-name <MAINTAINER_NAME>
          package.xml maintainer name (as `ros2 pkg create --maintainer-name`). Default: `git config user.name`

      --maintainer-email <MAINTAINER_EMAIL>
          package.xml maintainer email (as `ros2 pkg create --maintainer-email`). Default: `git config user.email`

      --destination-directory <DESTINATION_DIRECTORY>
          Directory to create the package in (as `ros2 pkg create --destination-directory`). Default: the current directory

      --component
          Scaffold a planned-mode component instead of a direct-mode binary project.
          
          A component is a reusable library node with an `nros::Component` and a folded `[component]` `nros.toml`. It is platform-agnostic (platform and RMW are chosen at deploy time), so `--platform` is not needed.

      --image <IMAGE>
          Scaffold an `[image.<name>]` — a buildable image — into the bringup package's `system.toml` instead of a project

      --host <HOST>
          Scaffold a `[host.<name>]` — a machine nodes run on — into the bringup package's `system.toml`

      --deploy <DEPLOY>
          Deprecated: use `--image` or `--host`.
          
          `[deploy.*]` split into `[image.*]` (what is built) and `[host.*]` (where it runs). Still accepted, and dispatched by `--kind`: `self` scaffolds a host, anything else an image.

      --workspace
          Scaffold a minimal multi-node workspace instead of a standalone project.
          
          The workspace holds node packages, a bringup and an entry: the canonical copy-out template with the RMW choice baked into every file that spells it. Defaults: `--lang cpp --rmw cyclonedds`.

      --from <PACKAGE>
          With `--workspace`: grow this single package into a workspace.
          
          Takes a package made by `nros new <name> --board <board>`. Its node moves to `<name>/src/<package>/` unchanged, and its `system.toml` moves to the bringup `<name>/src/<package>_bringup/`. `nros new node <name>` inside the workspace then adds a second node.

      --kind <KIND>
          `runner` or `command`: scaffold a runner or command package.
          
          The package holds its `package.xml`, its descriptor and a stub on `nros-extension` (`--lang rust`, the default) or a CMake executable that speaks the protocol JSON itself (`--lang cpp`). Inside a workspace it lands in `src/<name>/`. Check it with `nros check <name>`.

      --target <TARGET>
          Deprecated: accepted and ignored.
          
          The rustc triple comes from the board descriptor, so an image carries none.

      --board <BOARD>
          The board a package's one `[image.<id>]` names (`nros new <name> --board <board>`, the single-package front door: the platform is the board's), or the board an `--image` is built for. With `--platform` instead, a project defaults to the platform's own board from the board catalog (`freertos` -> `mps2-an385-freertos`) and refuses, naming the candidates, when the platform has several (`threadx`)

      --bringup <BRINGUP>
          Deploy mode: pick the bringup package whose `system.toml` to edit when the workspace exposes more than one

      --to <BRINGUP>
          Inside a workspace: the bringup that runs the new node package.
          
          `nros new <node> --to <bringup>` adds the package under `src/`, a `[[component]]` row for it in the bringup's `system.toml` and an `<exec_depend>` in its `package.xml`. Without `--to` no bringup is touched.

      --from-launch <FROM_LAUNCH>
          Deploy mode: also set the bringup `[system].default_launch` (bootstrap)

      --from-profile <FROM_PROFILE>
          Fork an existing block of the same table (`[image.<name>]` with `--image`, `[host.<name>]` with `--host`)

      --force
          Overwrite an existing directory / `[image.<name>]` or `[host.<name>]` table

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version

nros setup

Resolve + fetch a board's toolchain/SDK packages

Usage: nros setup [OPTIONS] [BOARD]
       nros setup <COMMAND>

Commands:
  board    Provision a downstream Zephyr consumer's tree for a nano-ros board
  presets  Write a project `CMakePresets.json` that includes the per-board presets `nros setup <board>` wrote. Then `cmake --preset <board>` works
  help     Print this message or the help of the given subcommand(s)

Arguments:
  [BOARD]
          Board to set up (resolves its toolchain/SDK package set from the index `[board.*]` table)

Options:
      --list
          List every package in the index + its version

      --licenses
          Show the license-gated packages + how to install them

      --offline-dirs
          Print the directories an air-gapped copy of this host's setup needs, one per line: the nros store, then the rustup and cargo homes the builds use (nros leaves Rust in rustup's own homes). Feed it to `tar`

      --tool <NAME>
          Install tools by name (instead of a board's whole set), e.g. `--tool qemu`. Repeatable, like `--source`: `--tool ninja --tool make` is ONE plan — one system-package ask for the union, one lock write. The `just <module> setup` recipes call this

      --source <SOURCES>
          Provision a single `[source.*]` package by name from the index.
          
          E.g. `--source freertos-kernel`. Repeatable. The index is the SSOT — `dest`/`ref`/`submodule` come from data, never a hardcoded path. The `just <module> setup` recipes call this instead of inlining `git submodule update <path>`.

      --build-sources
          Provision the whole build-stage source union the repo's tests need.
          
          That is what `just test` / `build-test-fixtures` need (every RMW's `-sys` source + the platform sources the workspace graph path-deps), independent of the per-board `nros setup <board>` slice. The index's top-level `build_sources` is the SSOT. With `--check`, only VERIFY they are present and name `nros setup --source <name>` per missing — the preflight the two recipes run.

      --prefix <PREFIX>
          Install prefix override (only with `--tool`): place the tool here instead of the shared store, e.g. `--prefix build/qemu` so the test harness finds it where it already looks. Layout is identical (`<prefix>/bin/…`)

      --index <INDEX>
          Path to the SDK index
          
          [default: nros-sdk-index.toml]

      --rmw <RMW>
          RMW backend whose host daemon/tool to also provision.
          
          Orthogonal to the board: `zenoh` | `xrce` | `cyclonedds`. Defaults to `zenoh`. Resolves `board.packages ∪ rmw.packages`.

      --dry-run
          Resolve + print the plan without fetching/building anything

      --full
          Provision full git history instead of the per-source shallow default (`--depth 1`). Use when you want `git log` / `blame` / branching in a provisioned source or submodule. Overrides the index `shallow` for this invocation only — no shared-file edit. (An already-shallow checkout is deepened in place with `git -C <path> fetch --unshallow`.)

      --shallow
          Force shallow (`--depth 1`) even for sources that set `shallow = false` in the index. The inverse of `--full`

      --system
          Print the native install command for the `[system.*]` OS packages.
          
          Resolves the `[system.*]` OS-package closure for the detected package manager and prints the one native install command (never runs it without `--sudo`). With `--check`, run each entry's presence probe instead and exit non-zero if anything is missing (the doctor surface).

      --workspace [<PATH>]
          Provision from what this workspace declares.
          
          Reads every `package.xml` under the path and answers three questions the tree already states: what the code depends on (`<depend>`), which builder must exist (`<build_type>` / `<buildtool_depend>`), and where it deploys (the `[image.<id>] board` of the `system.toml` beside a package.xml).
          
          Prints the plan, then installs it: every image's board and RMW in one store plan, then the OS-package closure — installed with `--sudo`, otherwise printed as the command to run. `--check` stops after the plan. Plain `nros setup` inside a workspace means `--workspace .`.

      --role <ROLE>
          Narrow `--system` to keys of these roles (repeatable).
          
          A scope's setup wants the HOST facts — `package` and `workspace` roles — and not `infra`: reporting every cross toolchain and emulator to someone provisioning `native` is noise, and noise is how a real missing package gets scrolled past.

      --check
          Run presence probes and report present/missing/unknown instead of installing/printing; exits 1 when anything is missing. With `--system`, probes only the `[system.*]` class; alone, walks EVERY declared class — `[system.*]`, `[rust.*]`, `[python.*]` — printing a remedy computed from each entry

      --sudo
          Execute the composed native install command instead of printing it.
          
          With `--system`, runs the native install command (which invokes sudo where the manager needs it). With `--tool`, a tool declaring its own `[tool.<name>] system = [..]` build deps installs them instead of printing a line to copy. With `<board>` and `--workspace`, the board plan's one system ask (its tools' and `[source.*]`s' `system = [..]`) is installed before any download. Any other use is refused.

  -j, --jobs <N>
          How many packages to install at once.
          
          Default: this host's CPU count; `NROS_SETUP_JOBS` overrides the default, and this overrides both.
          
          Expect less than N times faster: the link saturates long before the cores do, and a tool built from source already uses the whole machine, so source builds run one at a time and the overlap that pays is one package's build or unpack beside another's download. Output stays per package and in plan order whatever the value.

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version

nros setup board

Provision a downstream Zephyr consumer's tree for a nano-ros board.

Fetches the board's RMW source, applies the zephyr-line patch set, adds the rust targets, and checks the `zephyr-lang-rust` pin — driven by the board's provisioning contract (`board.cmake` / `[package.metadata.nros.board]`).

Usage: nros setup board [OPTIONS] --zephyr-workspace <ZEPHYR_WORKSPACE> <NAME>

Arguments:
  <NAME>
          Board crate suffix (after `nros-board-`), e.g. `fvp-aemv8r-smp`

Options:
      --zephyr-workspace <ZEPHYR_WORKSPACE>
          The downstream consumer's Zephyr workspace dir (the tree containing `zephyr/` + `modules/lang/rust/`). The patch set is applied here

      --workspace <WORKSPACE>
          nano-ros SDK root (where the board crate, `scripts/zephyr/`, and `nros-sdk-index.toml` live). Default: `$NROS_WORKSPACE_ROOT`, a checkout enclosing cwd, then this `nros` binary's own SDK root

      --index <INDEX>
          Path to the SDK index (relative paths resolve against the nano-ros workspace root). The RMW source's `dest` is index-driven
          
          [default: nros-sdk-index.toml]

      --dry-run
          Resolve + print the provisioning plan without fetching/patching

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version

Build

nros build

Build a nano-ros workspace.

Discovers packages, resolves the image, runs preflight, generates the root, and hands off to the native tool. The final stage is an `exec`, so compiler diagnostics are byte-identical to running cargo/cmake/west directly.

Usage: nros build [OPTIONS] [IMAGES]... [-- <NATIVE_ARGS>...]

Arguments:
  [IMAGES]...
          Image(s) to build — `linux`, or `<bringup>:linux` when two bringups declare the same id. Empty uses `[system] default_images`

  [NATIVE_ARGS]...
          Arguments after `--` go to the native tool verbatim

Options:
      --workspace <WORKSPACE>
          Workspace root. Defaults to the current directory

      --nano-ros-path <NANO_ROS_PATH>
          nano-ros SDK root holding `packages/boards`. Defaults to a walk-up from the workspace, then this `nros` binary's own SDK root

      --zephyr-workspace <DIR>
          The west workspace holding Zephyr — the directory that contains `zephyr/`. Zephyr images only.
          
          The explicit rung of the resolution ladder, above `$ZEPHYR_BASE` and `$NROS_ZEPHYR_WORKSPACE`. An environment variable is ambient state that a user has to remember to set and cannot see in the command they ran; this makes the same fact reviewable in a script and in shell history.
          
          Pointing it at the `zephyr/` directory itself also works — that is the commonest way to get this wrong, and both spellings name one place.

      --all
          Build every declared image

      --board <BOARD>
          Build the image whose `[image.*] board` is this board.
          
          Matches the authored word (any case), any alias of the same board descriptor, or the `nros setup` index key the board provisions through (`nros build --board mps2-an385-baremetal` finds a `baremetal` image). One match builds exactly that image, as if it were named; several or none is refused, listing them — the image id stays the unit. Not with image arguments or `--all`.

      --dry-run
          Print the stages and the command that would run, then stop.
          
          Safe by construction: a `Handoff` performs no I/O until `exec`. It still GENERATES (stage 4 writes each image's generated files), which regenerates an application without building it.

  -v, --verbose
          Also print the explanation behind each configure note.
          
          That is: why a pass re-runs, why a size was not derived. Sets `NROS_VERBOSE=1` for every native command; a correct build without it prints one line per fact.

      --explain-sizing
          Print, in full, every sizing input the image leaves to a default.
          
          A build prints them as one summary line; this names each one, why it was not derived, and what declaring it would take. `NROS_EXPLAIN_SIZING=1` asks the same of any road (a cmake or west configure).

      --offline
          Do not fetch anything; fail naming what is missing.
          
          Note this is a SCOPED guarantee: stages 1–4 touch no network, and stage 5 gets the native tool's own offline spelling. It cannot promise an arbitrary user `CMakeLists.txt` refrains from fetching.

      --packages-select <PKG>...
          Only these packages — no dependencies, no dependents.
          
          colcon's flag, with two differences: a name matching no package is an error, not a warning, and a selection that leaves out a package a selected one depends on is refused, since there is no install prefix for it to come from. That holds for every selection flag.

      --packages-up-to <PKG>...
          These packages and everything they depend on, transitively.
          
          The selection flags compose as an INTERSECTION, which is colcon's composition too: each deselects independently, so adding one can only ever narrow the set.

      --packages-above <PKG>...
          These packages and everything that depends on them, transitively.
          
          A package here that depends on a workspace package left out is refused, as for every selection flag; add `--packages-up-to` for its dependencies. A cargo member with no `package.xml` is refused here: its dependents name it only in their `Cargo.toml`, which the selection does not read.

      --packages-skip <PKG>...
          Leave these packages out

      --base-paths <PATH>...
          The workspace's source roots, relative to the workspace (default: `.`, plus `nros.toml` `package_paths`).
          
          They replace the workspace and its `package_paths`, and nothing else: the nano-ros packages and `NROS_PACKAGE_PATH` stay on the search path. As in colcon, the roots are peers searched recursively, their order does not matter, a path repeated or inside another counts once, and a package name found in two of them is an error. A path that does not exist is an error; one that holds no package is a warning.

      --continue-on-error
          Keep building the other packages when one fails.
          
          A package that depends on a failed one is skipped, as with colcon, and the command still exits non-zero, with the first failure's status. In a workspace with images, the unit is the image: each image is one merged build, so a failure inside it fails the whole image, and the next image is still attempted.

      --cmake-args <ARG>...
          Arguments passed to every CMake configure: a cmake image's, a west image's (after west's own `--`), and a cmake package's.
          
          A cargo image runs no CMake configure and ignores them, as colcon ignores them for a package that is not a CMake package. Ends at the next `nros build` flag or at `--`, as colcon's does.

  -j, --jobs <N>
          Run at most N jobs at once, in total. Default: the number of CPUs.
          
          Every tool below `nros build` (cargo, make, ninja, west's cmake) shares one GNU make jobserver of N tokens, so packages compiling side by side still run N jobs in total, not N each. A package starts once every package it depends on has finished; images build one at a time, each drawing on the same N. Under a `make -jN` that already provides a jobserver, `nros build` joins it instead. Ninja older than 1.13 does not read a jobserver and runs at its own width; a warning names it.

      --build-base <DIR>
          Where each package's build directory goes: `<DIR>/<package>/`. Default: `build`, under the workspace.
          
          Only for a workspace with no bringup. An image's generated tree has a fixed place under `build/`, which the cmake module and the image's other readers all expect, so moving it for one build would split them; it is refused there.

      --check[=<TOOL>]
          Type-check the image instead of building it: `cargo check`, or `cargo clippy` with `--check=clippy`.
          
          Everything before the cargo command is the same as a build — the generated message crates, the `<pkg>_nros_selection` crate, the image's settings file and its lock — because none of it is optional for a check either: a leaf whose manifest names the selection crate cannot even be LOADED until sync has written it, so a bare `cargo check` in a fresh checkout fails at manifest parse with an error that never says why. Only the final verb changes, so a check here and a build here see one dependency graph.
          
          Cargo images only; a cmake or west image is refused, since neither tool has a check that is not a build.

          Possible values:
          - check:  `cargo check`
          - clippy: `cargo clippy`. Lint flags go after a second `--`: `nros build --check=clippy -- -- -D warnings`

      --allow-overriding <NAME>...
          Let a package replace another provider of this name, for this build only.
          
          colcon's flag. A replacement of the nano-ros provider nobody declared is refused for a runner or a command, and the same name in two source trees (the workspace and a `package_paths` entry) is refused for every kind; with this flag the later root wins. To make a choice permanent, add `<name> = "<package path>"` under `[workspace.overrides]` in `nros.toml` instead.

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version

nros configure

Configure a project: generate message bindings and the cargo patch config, then resolve and generate every image's build inputs.

The message bindings and patch config, then the stages `nros build` runs before it builds (discover, preflight, census, resolve, generate), under a per-project lock. Runs no target build tool. Records a stamp per image, so a rerun with nothing changed is a no-op. An image this host cannot build is skipped unless named.

Usage: nros configure [OPTIONS] [WORKSPACE]

Arguments:
  [WORKSPACE]
          Workspace root (the dir containing `src/`). Defaults to cwd

Options:
      --generated-base <DIR>
          Output dir for the generated message crates, relative to the workspace. Models and other sync output stay under `build/`
          
          [default: generated]

      --ros-edition <ROS_EDITION>
          ROS 2 edition (`humble` | `iron` | `jazzy`).
          
          When omitted, inherits `[system].ros_edition` from a `system.toml` at the workspace root, else `humble`.

      --image <ID>
          Single-package leaf only: sync for this `[image.<id>]`.
          
          Covers its selection package, its `build/<id>/nros-cargo.toml`, and message codegen for its ROS edition. A leaf may declare one image per RMW and edition; without this flag the leaf's own rule applies (one image, or `[system] default_images`).

      --dry-run
          Don't write — just print what would happen

      --check
          Exit non-zero if any patch block is missing or stale (CI hook; also used by `nros ws status`)

  -v, --verbose
          Verbose codegen output

      --nano-ros-root <DIR>
          nano-ros source tree to scan as the FIRST provider search root.
          
          The same root every provider lookup reads, so the provider index this writes is the one later commands read.

      --base-paths <PATH>...
          The workspace's source roots, relative to the workspace (default: `.`, plus `nros.toml` `package_paths`).
          
          They replace the workspace and its `package_paths`, and nothing else: the nano-ros packages and `NROS_PACKAGE_PATH` stay on the search path. As in colcon, the roots are peers searched recursively, their order does not matter, a path repeated or inside another counts once, and a package name found in two of them is an error. A path that does not exist is an error; one that holds no package is a warning.

      --no-provider-index
          Skip the provider index entirely (`<ws>/build/nros/providers.json`).
          
          The index is a CACHE for later commands, not an input to this sync, so a caller that will not read it can skip the scan outright. Same shape as `--no-metadata` above: name the expensive optional step and let the caller decline it.

      --model-dir <MODEL_DIR>
          Write resolved SystemModels here instead of into each bringup's `config/`.
          
          This makes them build output rather than committed source. Consumers find them through the same search order (`nros_orchestration_ir::model_location`): export `NROS_MODEL_DIR` to the same path for the build.

      --no-metadata
          Skip the source-metadata refresh.
          
          The refresh compiles a host probe per Node pkg, which is the slow part of a cold sync; skipping it leaves any existing sidecars untouched and makes bakes fall back to the SystemModel's entity lower bound.

      --nano-ros-path <NANO_ROS_PATH>
          The nano-ros SDK root the probes and board lookups read.
          
          Defaults to a walk-up from the workspace, then this `nros` binary's own SDK root. It adds nothing to the patch block: the canonical shape carries nros-* runtime crates as path-deps in the user's own `[dependencies]`, so duplicating them there triggers cargo's "patch unused" warnings.

      --offline
          Never touch the network. Passed to the `cargo update --workspace` that prunes a single-package leaf's freshly seeded `Cargo.lock`, the one step of a sync that resolves crates

      --force
          Configure even when every image's stamp is current

      --census [<BRINGUP:IMAGE>]
          Take the entity census first: build the native image generated from the same launch file, run it, and record what it registers. Every image this configure covers, or only `BRINGUP:IMAGE`: the image whose build checks the census, usually a cross image, as in `nros build BRINGUP:IMAGE`. A plain configure only reports a census that is missing or stale, because taking one builds and runs a program

      --migrate
          Apply the known, reversible layout migrations first, printing every file moved. Today that is one: a `system.toml` beside a package's code moves into a bringup package

  -h, --help
          Print help (see a summary with '-h')

nros update

Move one pin, editing the pin set and leaving one diff.

A pin is a registry crate (`--crate`), a vendored source (`--source`), a host tool (`--tool`) or a west project (`--west`).

Usage: nros update [OPTIONS] <--pins|--crate <NAME>|--source <NAME>|--tool <NAME>|--west <MODULE>>

Options:
      --pins
          Regenerate the registry pin set from the locked roots as they stand — after a `cargo update` or a manifest edit in one root. Disagreements between roots are settled upward first

      --prune
          With `--pins`: also DROP every pinned range no locked root resolves and `locks/leaf-only-pins.toml` does not keep. Regeneration alone never drops a range, so a bump leaves the old one pinned

      --crate <NAME>
          Move a Rust registry crate's pin: every locked root that uses it is re-resolved with `cargo update`, the roots are brought into agreement, and the pin set is regenerated from them

      --precise <VERSION>
          The exact version to move to. Without it, cargo picks the newest semver-compatible one. A different MAJOR is a manifest edit first

      --source <NAME>
          Move a vendored source (`[source.<name>]`) to a commit: its submodule is checked out there and the index `ref` rewritten, forward only

      --ref <SHA>
          The commit for `--source`

      --allow-rewind
          Let `--source` move a pin BACKWARDS (the submodule-pin rule forbids it otherwise; say why in the commit)

      --tool <NAME>
          Move a host tool (`[tool.<name>]`) to a version: the row's version strings are rewritten and every dist artifact is downloaded to recompute its sha256

      --to-version <VERSION>
          The version for `--tool`

      --west <MODULE>
          Move a Zephyr west project's revision in every manifest that lists it

      --revision <REV>
          The revision for `--west`

      --nano-ros-path <NANO_ROS_PATH>
          The nano-ros checkout whose pin set to edit (else the usual ladder)

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version

nros locate

Print where a resource is, and with `--why`, which rung answered.

The cmake/just/shell front door to `nros_build_paths::locate`.

Usage: nros locate [OPTIONS] [NAMES]...

Arguments:
  [NAMES]...
          Resources to locate: a `[source.<name>]` of the index, or `store` / `nano-ros` for the two roots. `artifact <name>…` instead locates a cargo-built artifact (`c-archive`, `cpp-archive`, `c-include`, `cpp-include`, `c-config-header`, `cpp-config-header`); `tool <name>` a host binary (`nros-launch-resolve`, `renode`, or `qemu-system-<arch>` through the one QEMU ladder), the install directory of an SDK tool `nros setup <board>` provisioned (`tool zephyr-sdk`), or `configured` where `nros configure` put an image's answer (with `--project` and `--image`)

Options:
      --all
          Every `[source.*]` row. A row that resolves nowhere is skipped in batch output (and named on stderr), never invented

      --why
          Print every rung and what it saw

      --format <FORMAT>
          Possible values:
          - path:  The path alone (one name) or `name<TAB>path` lines
          - sh:    `NROS_LOCATE_<NAME>=<path>` lines, shell-quoted
          - cmake: `set(NROS_LOCATE_<NAME> "<path>")` lines — normal variables, never CACHE
          
          [default: path]

      --index <INDEX>
          Path to the SDK index
          
          [default: nros-sdk-index.toml]

      --target <TARGET>
          `artifact` mode: the target triple the artifact was built for. Omit for a host build cargo ran without `--target`

      --profile <PROFILE>
          `artifact` mode: the cargo PROFILE (`dev`, `release`, a custom one)
          
          [default: release]

      --target-dir <TARGET_DIR>
          `artifact` mode: the cargo target dir. Default: cargo's own answer for the nano-ros workspace (`CARGO_TARGET_DIR`, `[build] target-dir`, else `<root>/target`)

      --placed-dir <PLACED_DIR>
          `artifact` mode: the directory a build PLACED its config headers in.
          
          REQUIRED for the header artifacts, which live only in cargo's `$OUT_DIR`; an archive is never placed, so naming one with this is refused.

      --image <IMAGE>
          `configured` mode: the image, by its configure key (an image id for a single-package leaf, `<bringup>:<id>` for a workspace)

      --project <PROJECT>
          The project whose `system.toml` `[sources]` is rung 3.
          
          Default: `$NROS_WORKSPACE_ROOT`, else the nearest ancestor of the working directory that holds a `system.toml`.

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
