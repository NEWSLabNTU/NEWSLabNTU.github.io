Lab: QoS is checked twice

Tutorial · Level 2: Building real applications

Needs first: Add a second node

Status: this chapter runs on nros-board-mps2-an385: Verified in emulator (daily); nros-board-mps2-an385-freertos: Verified in emulator (daily). From the board support registry; Board Support Levels explains the words.

A ROS 2 publisher and subscription agree on QoS when they meet, at run time, and a mismatch shows up as messages that never arrive. On a microcontroller there is no one watching at run time, so nano-ros checks the agreement earlier, and twice: when the image is built, against the other nodes of the system, and when the image boots, against what your code asked for. In this lab you break each check on purpose, read what it says, and then make the two nodes of chapter 3 agree on a non-default QoS: the talker keeps its last message for a subscriber that joins late (transient_local durability), and the listener asks for it.

At the end, nros run prints I heard: again, from a pair that agrees on transient_local in its code and in its contract.

The lab starts from the workspace of chapter 3: sensor_node publishes on /chatter and monitor_node subscribes to it. Run every step from the root of sensor_ws, in a shell where ROS 2 is sourced. It takes about an hour, most of it reading.

What transient_local buys, and costs

A volatile publisher sends each message to the subscribers that exist when it publishes, and forgets it. A subscriber that starts a second later has missed it for good. A transient_local publisher keeps its last messages and hands them to a subscriber that joins later, which is what a topic that changes rarely needs: a map, a configuration, a robot’s mode. A node that boots late, or restarts, still learns the current value without waiting for the next change.

On a workstation the kept messages live in a heap the middleware grows as it likes. On a microcontroller every kept message is a buffer fixed when the image is built, so the build must know which publishers keep messages and how many. That is why the choice belongs in the contract as well as in the code: the contract is what the build sizes from, and the code is what runs.

The contract the scaffold wrote

The bringup holds a contract beside system.toml. The scaffold wrote the talker’s row when it made the workspace, and nros new --to added the listener’s in chapter 3:

cat src/sensor_node_bringup/system.contract.yaml

The part that matters (comments trimmed):

nodes:
  sensor_node:
    params: {}
    paths:
      on_tick:
        trigger: { timer: { rate_hz: 1 } }
        output: [chatter]
    pub:
      chatter:
        qos:
          durability: volatile
  monitor_node:
    params: {}
    sub:
      chatter:
        qos:
          durability: volatile

A contract row states what a node creates and with which QoS. The build sizes the image from it (chapter 8 shows how much that saves), and, which is this lab’s subject, checks it. Both rows say volatile, which is what the scaffolded code asks for, so the two checks have nothing to say yet. Every node has a params: line, even an empty one: the build sizes the parameter store from every node’s declaration or from none, and a contract that states some nodes and not others is refused.

Check one: the build compares the nodes

Change monitor_node’s row to ask for more than the talker offers: a transient_local subscription, against a volatile publisher. Replace the contract with:

cat > src/sensor_node_bringup/system.contract.yaml <<'EOF'
version: 1

nodes:
  sensor_node:
    params: {}
    paths:
      on_tick:
        trigger: { timer: { rate_hz: 1 } }
        output: [chatter]
    pub:
      chatter:
        qos:
          durability: volatile

  monitor_node:
    params: {}
    sub:
      chatter:
        qos:
          durability: transient_local

topics:
  /chatter:
    type: std_msgs/msg/String
    pub: [sensor_node/chatter]
    sub: [monitor_node/chatter]
    # Read outside this workspace, by `ros2 topic echo` or a ROS 2 node.
    external: sub
EOF

params: {} says the node declares no parameters. A C or C++ bringup needs the key on every row or on none, so write it on both.

Build:

nros build 2>&1 | tee build/qos-check-one.log || true
grep 'qos-match' build/qos-check-one.log

The tee keeps the output in a file, so the grep can show the line that matters. The build stops before it compiles anything:

error: [qos-match] error: incompatible QoS on topic '/chatter' field 'durability': pub '/sensor_node/chatter' offers 'volatile', sub '/monitor_node/chatter' requests 'transient_local' (at topics./chatter.qos.durability)
Error: refusing to emit a SystemModel: 2 contract error(s) (run `check` on the same launch file for source excerpts)

This is the rule ROS 2 applies when the two endpoints meet, “requested versus offered”: a subscription may ask for less than the publisher offers, never more. A transient_local subscription wants the samples published before it joined, and a volatile publisher keeps none. ROS 2 would connect nothing and report an incompatible-QoS event at run time, if anyone listened for it. Here both rows are in one file, so the build compares them first and names the topic, the field and both endpoints.

Check two: the boot compares the contract with the code

Make the talker offer what the listener asks for, in the contract only. Change the publisher’s row:

sed -i 's/durability: volatile/durability: transient_local/' \
    src/sensor_node_bringup/system.contract.yaml

The two rows agree now, and the build accepts them. Run it:

nros run --expect 'I heard:' --timeout 300 2>&1 | tee build/qos-check-two.log || true
grep 'declared QoS' build/qos-check-two.log
grep 'would widen what the code narrowed' build/qos-check-two.log

The image builds and boots, then stops. Its console (a C project’s, trimmed; the Rust one prints the same lines with a timestamp):

[WARN] nros: declared QoS: taking durability transient_local on publisher `/chatter`; the call site asked volatile. Change the contract row to keep the call site's.
[ERROR] nros: declared QoS: subscription `/chatter` registers volatile and the contract declares durability transient_local; taking it would widen what the code narrowed. Fix the contract row or the call site.
nros run: the target exited with code 1 after 2.5 s without `I heard:`

When a node creates an endpoint, nano-ros compares the QoS the code passed with the contract’s row for it, and the two lines are the two directions of that rule:

  • A publisher’s row may strengthen the call site. The code asked for volatile; keeping one sample for a late subscriber costs the image a buffer the build already reserved from the row, and every subscriber the publisher served before is still served. So the image takes the row’s value and warns, naming both.
  • A subscription’s row may not widen what the call site narrowed. The code subscribed volatile, which is the narrower request; the row claims transient_local. Taking the row would hand the callback samples published before it joined, which the code never asked for and may not handle. So the image refuses to create the subscription, and the boot fails with DeclaredQosMismatch.

The contract describes the code; it does not replace it. Where they disagree, the safe direction is taken with a warning, and the unsafe one is refused.

Make the code say it

Change both call sites to transient_local, so the code and the contract say the same thing.

The talker creates its publisher in src/sensor_node/src/lib.rs with create_publisher_for_topic; the _with_qos form takes a QoSProfile:

#![allow(unused)]
fn main() {
let pub_chatter = node.create_publisher_for_topic_with_qos::<StringMsg>(
    "/chatter",
    QoSProfile::default().transient_local(),
)?;
}

The listener’s create_subscription_for_callback_name has no QoS form; the one that does, create_subscription_for_topic_with_qos, names the callback after the topic, so on_callback matches "/chatter" instead of "on_chatter":

#![allow(unused)]
fn main() {
let _sub = node.create_subscription_for_topic_with_qos::<StringMsg>(
    "/chatter",
    QoSProfile::default().transient_local(),
)?;
}

Both files import QoSProfile from nros. By hand, or:

sed -i -e 's#^use nros::{#use nros::{QoSProfile, #' \
    -e 's#create_publisher_for_topic::<StringMsg>("/chatter")#create_publisher_for_topic_with_qos::<StringMsg>("/chatter", QoSProfile::default().transient_local())#' \
    src/sensor_node/src/lib.rs
sed -i -e 's#^use nros::{#use nros::{QoSProfile, #' \
    -e 's#create_subscription_for_callback_name::<StringMsg>("on_chatter", "/chatter")#create_subscription_for_topic_with_qos::<StringMsg>("/chatter", QoSProfile::default().transient_local())#' \
    -e 's#callback.as_str() == "on_chatter"#callback.as_str() == "/chatter"#' \
    src/monitor_node/src/lib.rs

The talker creates its publisher in src/sensor_node/src/Talker.c with rclc_publisher_init_default; the _with_qos form takes an rclc_qos_t. Start from the default profile and change one field:

rclc_qos_t qos = RCLC_QOS_DEFAULT;
qos.durability = RCLC_QOS_DURABILITY_TRANSIENT_LOCAL;
rcl_ret_t rc = rclc_publisher_init_with_qos(
    &self->pub, node, ROSIDL_GET_MSG_TYPE_SUPPORT(std_msgs, msg, String), "/chatter", &qos);

The listener’s src/monitor_node/src/Listener.c does the same with rclc_subscription_init_with_qos. By hand, or:

sed -i -e 's#rcl_ret_t rc = rclc_publisher_init_default(#rclc_qos_t qos = RCLC_QOS_DEFAULT;\n    qos.durability = RCLC_QOS_DURABILITY_TRANSIENT_LOCAL;\n    rcl_ret_t rc = rclc_publisher_init_with_qos(#' \
    -e 's#String), "/chatter");#String), "/chatter", \&qos);#' \
    src/sensor_node/src/Talker.c
sed -i -e 's#rcl_ret_t rc = rclc_subscription_init_default(#rclc_qos_t qos = RCLC_QOS_DEFAULT;\n    qos.durability = RCLC_QOS_DURABILITY_TRANSIENT_LOCAL;\n    rcl_ret_t rc = rclc_subscription_init_with_qos(#' \
    -e 's#String), "/chatter");#String), "/chatter", \&qos);#' \
    src/monitor_node/src/Listener.c

The talker creates its publisher in src/sensor_node/src/Talker.cpp, and the listener binds its subscription in src/monitor_node/src/Listener.cpp. Both take a QoS after the topic name, the way rclcpp does:

::rclcpp::Result r = node.create_publisher(
    pub_, "/chatter", ::rclcpp::QoS::default_profile().transient_local());

::rclcpp::bind_subscription<::std_msgs::msg::String, Listener, &Listener::on_msg>(
    node, "/chatter", this, ::rclcpp::QoS::default_profile().transient_local());

By hand, or:

sed -i 's#node.create_publisher(pub_, "/chatter");#node.create_publisher(pub_, "/chatter", ::rclcpp::QoS::default_profile().transient_local());#' \
    src/sensor_node/src/Talker.cpp
sed -i 's#node, "/chatter", this);#node, "/chatter", this, ::rclcpp::QoS::default_profile().transient_local());#' \
    src/monitor_node/src/Listener.cpp

Run the pair

nros run --expect 'I heard:'

I heard:
nros run: matched after

The image boots, and the listener hears the talker. The console still carries warnings, of a different kind (trimmed):

[WARN] nros: qos: publisher '/chatter' asked for TRANSIENT_LOCAL KEEP_LAST(10); this image retains 1 sample(s) per transient-local publisher and replays them on a late joiner's query. Granting 1 and advertising it to the graph.
[WARN] nros: qos: subscription '/chatter' asked for KEEP_LAST(10); this image's receive ring holds 4. Granting 4 and advertising it to the graph. Raise NROS_ZENOH_SUBSCRIBER_RING_DEPTH to keep more.
I heard: [Hello World: 1]

These are not mismatches between the code and the contract. They are the image granting less depth than the code asked for: QoSProfile::default(), RCLC_QOS_DEFAULT and QoS::default_profile() all ask for KEEP_LAST(10), and this image keeps one sample per transient-local publisher and four per subscription. The image grants what it has, advertises the granted value to the ROS 2 graph (so ros2 topic info -v /chatter shows the truth), and names the knob that would raise it.

Change it

Silence the depth warnings by asking for what the image grants. Add depth: 1 beside durability in both contract rows, and ask for depth 1 at both call sites: .keep_last(1) on the Rust QoSProfile, qos.depth = 1; in C, .keep_last(1) on the C++ QoS. Run again: the qos: lines are gone, and the image reserves one sample per endpoint instead of the default ring.

Then try the other direction of check two: put the talker’s contract row back to volatile while its code keeps transient_local. The build refuses it first (check one, since the listener still asks for transient_local); make the listener volatile in both places too, and read what the boot says about a publisher whose row is weaker than its call site.

If it doesn’t work

  • Step one builds instead of refusing: compare the file with the one above. The listener’s row must sit under nodes: with the name monitor_node, and /chatter under topics: must list monitor_node/chatter in its sub:, so the build knows the two rows meet on one topic.
  • Step two fails without a declared QoS line: the build itself failed, before the image booted. Read the first error in its output; a C or C++ bringup refuses a contract where some rows carry params: and others do not.
  • The last run prints declared QoS errors again: one call site still asks for volatile. Each line names the endpoint (publisher or subscription) and its topic.
  • The listener prints nothing in the last run: in a Rust project, on_callback still matches "on_chatter". The _with_qos subscription names its callback after the topic.

What just happened

You met the two places a nano-ros system’s QoS is checked, and the rule each applies:

WhenComparesRuleOn a mismatch
build (qos-match)a subscription’s row with its publisher’s rowthe subscription may request no more than the publisher offersthe build refuses and names topic, field and both endpoints
boot, publisherthe call site with the rowthe row may strengthen the call site, never weaken itstronger: taken, with a warning; weaker: refused
boot, subscriptionthe call site with the rowthe row may not widen what the call site narrowedrefused (DeclaredQosMismatch)
boot, any endpointthe asked depth with the image’s poolsthe image grants what it hasgranted and advertised, with a warning naming the knob

In ROS 2, all of this happens when two endpoints meet on the network, and a mismatch is a topic that stays silent. nano-ros states the system in one contract, so the comparison between nodes moves to the build, and the comparison between the contract and the code happens once, at boot, before any message flows. What remains at run time is the same “requested versus offered” check with peers outside the image, such as ros2 topic echo.
