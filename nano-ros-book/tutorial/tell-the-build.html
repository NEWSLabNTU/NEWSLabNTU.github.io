Tell the build what your system creates

Tutorial · Level 2: Building real applications

Needs first: Parameters and launch files

Status: this chapter runs on nros-board-mps2-an385: Verified in emulator (daily). From the board support registry; Board Support Levels explains the words.

Every node in the project creates publishers, subscriptions, timers, servers and clients when it starts. On this board, the memory for all of them is set aside when the image is built, so the build must size it before any node has run. Until now it has not known what the nodes create, so it sized every pool for a generous default. In this chapter you write the contract: a file beside the launch file that states what the system creates. You measure the image’s static RAM before and after, and watch it fall by more than a third:

   text    data     bss     dec     hex filename
1132064    6288  613540 1751892  1abb54 .../baremetal_entry      (before)
1131656    4656  384484 1520796  17349c .../baremetal_entry      (after)

Then you break the contract on purpose and read the refusal, which shows what the build does when a statement and the system disagree.

Run every step from the root of sensor_ws.

Measure the image as it is

nros build prints the path of the image it built, after artifact:. The step keeps a copy of the build’s output in build/build.log, so a failed build still shows you why, and reads the path from there. Read the image’s sizes with the size tool of the Arm toolchain nros setup installed:

nros build 2>&1 | tee build/build.log
elf="$(sed -n 's/^  artifact: //p' build/build.log)"
"$(nros locate tool arm-none-eabi-gcc)/bin/arm-none-eabi-size" "$elf"

   text    data     bss     dec     hex filename
1132064    6288  613540 1751892  1abb54 /home/you/sensor_ws/build/bare-metal-zenoh/baremetal_entry/target/thumbv7m-none-eabi/debug/baremetal_entry

Those are the numbers of a Rust project; a C or C++ project’s differ, and its image is under build/ too. text is flash: the code and its constants. data and bss are RAM that exists from the moment the board boots, data with initial values and bss zeroed. This image claims 613,540 bytes of zeroed RAM before its first instruction, which is what this chapter shrinks. The build is a debug build, so text is large; bss is not affected by optimization.

Where does it go? Each node’s slots, the executor’s storage for every callback, the middleware’s sessions and receive buffers, and a parameter store, each sized for the most the system might create: up to 32 parameters, four samples per subscription, and so on. The build warned about some of it on every run, in lines like this one:

warning: nros-rmw-zenoh@0.6.0: the parameter family's requests are not priced: the image declares no `params:`. Its inbox slot keeps 1024 B; a larger `set_parameters` is dropped with no reply. Declaring the parameters in the contract derives it ...

Write the contract

A contract is a YAML file with the launch file’s name and .contract.yaml, in the same directory. Write launch/system.contract.yaml:

cat > src/sensor_node_bringup/launch/system.contract.yaml <<'EOF'
# What the system in system.launch.xml creates, so the build can size the
# image for exactly that. Names are the names the code and the launch file
# give: local endpoint names under nodes:, resolved names under topics:.
version: 1

nodes:
  sensor_node:
    params:
      period_ms: { type: integer }
    paths:
      on_tick:
        trigger: { timer: { rate_hz: 2 } }
        output: [reading]
    pub:
      reading: { qos: { depth: 1, durability: volatile } }
  monitor_node:
    params: {}
    sub:
      reading: { qos: { depth: 1, durability: volatile } }
  server_node:
    params: {}
    srv:
      add_two_ints: {}
  client_node:
    params: {}
    paths:
      issue_call:
        trigger: { timer: { rate_hz: 1 } }
        output: []
    cli:
      add_two_ints: {}
  action_server_node:
    params: {}
  action_client_node:
    params: {}

topics:
  /sensor/reading:
    type: tutorial_msgs/msg/Reading
    pub: [sensor_node/reading]
    sub: [monitor_node/reading]

services:
  /add_two_ints:
    type: example_interfaces/srv/AddTwoInts
    server: [server_node/add_two_ints]
    client: [client_node/add_two_ints]

actions:
  /fibonacci:
    type: example_interfaces/action/Fibonacci
    server: [action_server_node/fibonacci]
    client: [action_client_node/fibonacci]
EOF

Read it from the top:

  • nodes: has one entry per node, under the name the launch file gives it. Under each, the endpoints the node creates are keyed by their LOCAL name: reading, not /sensor/reading. pub:, sub:, srv: and cli: are publishers, subscriptions, service servers and service clients.
  • params: lists the parameters a node declares. The talker declares period_ms, the one chapter 7’s launch file sets; every other node declares none, params: {}. That is not the same as leaving params: out, which says nothing.
  • paths: is where timers live. A path with a timer trigger and no input is a periodic callback: the talker’s on_tick at 2 Hz (the 500 ms of chapter 7) and the client’s issue_call at 1 Hz.
  • qos: states the quality of service an endpoint uses. depth: 1 keeps one sample, and durability: volatile keeps none for late joiners.
  • topics:, services: and actions: wire the endpoints together under their RESOLVED names, and carry their types. /sensor/reading is the name after chapter 7’s remap, which is the name the board uses.

The build reads this file every time it builds the image, folds it into the system it resolved from the launch file, and sizes every pool from it. Nothing in a node package changes. The contract describes this launch file’s system, so a second launch file in the bringup gets its own contract, with its own name before .contract.yaml.

Mark the contract as unchecked

A contract is a statement beside the code, and the build can check it against the code by building the same launch file for your host, running that host program once in a recording mode, and comparing what the nodes created with what the contract says. That check is the census. It needs a host image of the same launch file in the bringup, and this one has only the board’s, so tell the build to warn rather than refuse when no census exists:

printf '\n[census]\non_missing = "warn"\n' >> src/sensor_node_bringup/system.toml

Every build of the image now says, in its output, that its pools come from a contract nothing has compared with the code. Treat that line as a reminder: the contract is yours to keep right until a census checks it.

Measure it again

nros build 2>&1 | tee build/build.log
elf="$(sed -n 's/^  artifact: //p' build/build.log)"
"$(nros locate tool arm-none-eabi-gcc)/bin/arm-none-eabi-size" "$elf"

   text    data     bss     dec     hex filename
1131656    4656  384484 1520796  17349c /home/you/sensor_ws/build/bare-metal-zenoh/baremetal_entry/target/thumbv7m-none-eabi/debug/baremetal_entry

Static RAM fell from 613,540 to 384,484 bytes of bss, and data from 6,288 to 4,656: 230,688 bytes, 37 percent of the image’s RAM, from a file of about 50 lines. Most of it is the parameter store, now sized for the one parameter the system declares instead of 32. The rest is the middleware’s receive buffers for one sample instead of four, and no retention for late joiners.

Run it

The image runs as before, with less RAM:

source /opt/ros/humble/setup.bash
nros run --expect 'I heard: reading 3'

I heard: reading 3

The console says where the depth now comes from:

[WARN] nros: [    0.089222] declared depth: taking KEEP_LAST(1) on publisher `/sensor/reading`; the call site asked 10 and the build reserved 1. Raise the contract row to keep more (type `tutorial_msgs::msg::dds_::Reading_`).
[INFO] sensor_node: [    0.100442] Publishing every 500 ms

The talker’s code asks for a history of 10, the ROS 2 default; the image reserved 1, because the contract says the system keeps 1, and the board takes what was reserved. The talker publishes every 500 ms and the listener reads each sample before the next arrives, so one is enough. A node that needs to keep more says so in the contract, and the build reserves it.

Break it on purpose

Rename the talker’s parameter in the contract, from period_ms to period:

sed -i 's#      period_ms: { type: integer }#      period: { type: integer }#' \
    src/sensor_node_bringup/launch/system.contract.yaml

and build:

if nros build; then echo "the build accepted a contract that disagrees with the launch file" >&2; exit 1; fi

The build refuses, before it compiles anything:

Error: 1 launch parameter value(s) disagree with the contract's declarations:
  node `/sensor_node`: parameter `period_ms`, set by launch file system.launch.xml, is not declared in its contract (/home/you/sensor_ws/src/sensor_node_bringup/launch/system.contract.yaml); it declares: period

The launch file sets period_ms, and the contract says the talker declares only period. The build does not guess which one is right, and it does not size the parameter store for the names that matched and ignore the rest. It stops, naming the node, the parameter and both files. The model it resolved is set aside as refused, so nothing builds from it until a resolve succeeds.

Put the name back, and the build succeeds again:

sed -i 's#      period: { type: integer }#      period_ms: { type: integer }#' \
    src/sensor_node_bringup/launch/system.contract.yaml
nros build

What just happened

You gave the build the contract, and it used it for static sizing: every pool of the image sized from what the system states it creates, rather than from a default large enough for any system.

A contract states, ahead of the build, what only exists after the program runs. A node creates its publishers and timers in register or configure, at boot, but the pools they live in are static arrays whose sizes are compiled in before any node’s code is. Somebody must state those numbers before the build, and the contract is where the whole system states them once, under the same names the launch file and the ROS 2 graph use.

Three rules make it safe to size from a statement:

  • Names are resolved names. A contract row matches an endpoint, a parameter or a node by the name the system actually uses, after remaps and namespaces. A row that matches nothing is not used, and a value the launch file sets that the contract does not declare is refused, as you saw.
  • All or nothing, per image. If one node of an image is missing from the contract, that image derives nothing and keeps its configured defaults. A count taken over only the nodes the contract describes would be smaller than the image needs, and a pool one slot short fails at boot, so the build refuses to guess “some of them”.
  • Checked against the code when it can be. The census compares the contract with what the nodes actually create. An endpoint the code creates and the contract omits is refused, because it is the pool that would be short; one the contract declares and the code never creates is refused too, unless the bringup waives it under [census.waive]. A census is fresh by content: touching a file changes nothing, adding a subscription does. This Tutorial’s bringup has no host image to take a census with, so it warns instead; [census] on_stale = "warn" does the same for a census that no longer matches the code.

The same contract works for every language. A C or C++ node package has no ENTITY_BOUNDS: its counts come only from the contract, which is why a contract matters most for a C or C++ image. A bringup with no launch/ directory writes the same file as system.contract.yaml beside its system.toml, and the build carries it to where the launch file is generated.

Design background

The contract and the sizing it drives follow RFC-0124 D6 for this walkthrough; the census follows the contract’s retirement of the per-component ENTITIES list, which declared counts beside the code with nothing comparing the two.
